# Moving from ItemsAdder

RP Engine reads ItemsAdder config files as they are. Copy a folder out of their
`contents/` — the configs at its root, `textures/` and `models/` beside them,
no `pack.yml` — into `plugins/RPEngine/content/` and start the server.

```
plugins/RPEngine/content/
  my_content/            ← straight out of ItemsAdder's contents/
    my_config.yml
    textures/
    models/
```

There is nothing to turn on. A file is recognised by its own shape — an
`info:` block beside `items:`, `font_images:` or `recipes:` — which nothing of ours looks
like, since our top-level keys are IDs. One of their files also works **inside**
a pack of yours, which is the useful shape for moving over a piece at a time.

## What comes across

| ItemsAdder | RP Engine |
|---|---|
| `items.<id>` | an [item](/rp-engine/items) |
| `resource.material` | `material` |
| `resource.textures` / `texture` | `texture` — the first one; a flat item has one picture |
| `resource.model_path` | `model` |
| `display_name` or `name` | `name` — both, since 4.0.9 renamed it |
| `lore`, `permission` | the same |
| `enchants`, `attribute_modifiers.mainhand` | `enchantments`, [`attributes`](/rp-engine/stats) |
| `durability.max_durability`, `unbreakable` | `durability`, `unbreakable` |
| `max_stack_size` | `stack` |
| `equipment.id` or `specific_properties.armor.custom_armor` | [`armor`](/rp-engine/armour), worn with that set's layer art |
| `equipments`, `armors_rendering`, `legacy_armor_renderings` | the layer art, read from any file in the pack |
| `equipment` with no `id`, on the head | `hat`, so a 3D helmet shows its model |
| `behaviours.liquid_bucket` | [`liquid`](/rp-engine/liquids) |
| `behaviours.furniture` | [`place:`](/rp-engine/models), with its light, solidity and seat |
| `blocks.<id>` | a [custom block](/rp-engine/blocks), with its model, hardness, light and tool |
| `behaviours.block` (or `specific_properties.block`) on an item | a [custom block](/rp-engine/blocks), with its name, lore, model (or the cube generated from its textures), hardness, tool and place sound |
| `loots.blocks.<name>`, in any file | the block's `drop`, when the table's first item is the pack's own and certain |
| `item_flags` | [`flags`](/rp-engine/stats) |
| `events` | [actions](/rp-engine/actions), below |
| `font_images.<id>` | an [icon](/rp-engine/icons) |
| `sounds.<id>`, with its subtitle, volume, pitch and stream | a [sound](/rp-engine/sounds), the subtitle looked up in your `minecraft_lang_overwrite` when it is a key |
| a `sounds.json` in `resourcepack/assets/<namespace>/`, from before 4.0.12 | a [sound](/rp-engine/sounds) per entry |
| `recipes.crafting_table`, `cooking`, `campfire_cooking`, `stonecutter` | [recipes](/rp-engine/recipes): shaped, the cookers (one each for a recipe with several `machines`), campfire and stonecutting |
| `recipes.smithing` | a `smithing` recipe |
| `recipes.anvil_repair` | an `anvil` repair, a quarter of full durability per ingredient, as theirs |
| `recipes.brewing` (from the ItemsAdderAdditions add-on) | a `brewing` recipe, which needs Paper; `minecraft:awkward_potion` is `potion/awkward` |
| `enabled: false` | skipped, as it is there |

A recipe's bare lowercase ID (`base: my_sword`) is the file's own namespace, as
ItemsAdder reads it. A recipe's `permission` is not carried across: RP Engine
recipes are open to everyone.

## Events become actions

| ItemsAdder event | RP Engine trigger |
|---|---|
| `interact.right`, `interact.left` (a bare `interact` is both) | `right_click`, `left_click` |
| `attack`, `drop`, `pickup`, `block_break` | the same |
| `eat`, `drink` | `consume` |
| `item_break` | `break` |
| `bow_shot` | `shoot` |
| `placed_block` / `placed_furniture`: `interact`, `break`, `place` | the block's or furniture's own [`interact`, `remove`, `place`](/rp-engine/actions#the-thing-in-the-world) |

Inside an event, `play_sound`, `execute_commands` (`as_console: true` runs as
the console, otherwise as the player), `potion_effect`, `give_item`,
`decrement_amount`, `cancel`, and ItemsAdderAdditions' `message` and
`actionbar` come across, in order. `{player}` means the same thing in both
plugins. A permission that every action in an event asks for becomes one
`permission` step at its front.

## What does not

Each of these is a **warning naming the ID** when the pack loads, never a
silence — a migration that quietly drops a third of somebody's pack is worse
than one that refuses out loud.

<Callout type="warning" title="A world of blocks does not come across">
  Block *definitions* translate. The blocks already standing in a world do not:
  the vanilla state each one hides in was allocated by ItemsAdder against its
  own numbering, so this engine reads them as whatever it gave that state. A
  pack migrates; a world has to be rebuilt or remapped by hand.

  Note also that the pool here is [smaller](/rp-engine/blocks) — 49 per note
  block base rather than 800 — because the instrument cannot be part of a
  block's identity. A pack with hundreds of blocks will not fit as it stands.
</Callout>

**Their entities** are a different feature rather than a different spelling,
and want writing as [`entities/`](/rp-engine/entities) definitions, which are
short. **Recipe groups other than the ones above** are skipped by name.

**Events and actions with nothing to land on**: holding, wearing, fishing, a
sneaking click, guns and books have no trigger here; particles, damage,
replacing blocks and dropping experience have no step. An action with a
`delay`, or with a permission only some of its event's actions share, is
skipped too, since a step runs when its trigger does and a permission step
stops everything after it. The rest of the event still comes across.

**Loot by chance**, and mob and fishing loot. A block gives back one thing, so
a table that might drop its item leaves the block dropping itself, and says so.

**Some of a sound.** A sound that picks one of several files at random keeps the
first, because an RP Engine sound plays one file, and `weight`,
`attenuation_distance`, `preload` and `jukebox` have no equivalent here. Your
audio stays where it is: their `sounds/` folder and resource pack folder are
both packed where an RP Engine sound looks.

## Two things worth knowing

**The folder name is the namespace.** A file whose `info.namespace` says
something else loads under the folder's name and warns you: the folder is what
the engine claimed, and IDs written elsewhere have to resolve to something.

**Their art lives at the pack root**, ours under `assets/`. Both are read, so
their `textures/item/ruby.png` and `models/lamp.json` need no moving — but if
you are writing new content beside it, `assets/` is the documented home and is
what the [content folder](/rp-engine/content) page assumes.

**Armour art stays where it is.** A set's `layer_1` and `layer_2` are exactly
the two pictures [vanilla's equipment path](/rp-engine/armour) draws, body and
leggings, so the build serves them there for you. That needs Minecraft 1.21.4;
on an older server the armour is still worn but draws with vanilla art, and the
build names every piece that will.

What does not come across from a set, each a warning naming the item: an
**animated** layer, which is a strip of frames a worn layer cannot play (save one
frame as `assets/textures/entity/equipment/humanoid/<id>.png`, or
`humanoid_leggings/` for legs); a `use_color` **tint** and **emissive** layers,
which needed ItemsAdder's shaders; and **colour-only** armour, which has no art
and is worn as plain leather.
