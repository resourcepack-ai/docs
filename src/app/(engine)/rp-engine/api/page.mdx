# Plugin API

Your own Spigot or Paper plugin can give a custom item, place a model, play an
emote, dress a player in 3D armour, park a vehicle and switch it off, put an
icon in a message, open a dialog with your own values on it, and cancel any of
those when your rules say no. Every snippet is shown in Java and Kotlin; pick
one and the rest of the docs follows your choice.

This page matches **RP Engine 0.2.10**, the current release.

## Setting up

RP Engine is not published to a Maven repository. Download `RPEngine.jar` from
[resourcepack.ai/rp-engine](https://resourcepack.ai/rp-engine) and compile
against the file. Use `compileOnly`: the server already has the plugin, and a
shaded second copy breaks class loading.

<CodeTabs labels={["Groovy", "Kotlin"]}>

```groovy
dependencies {
    compileOnly 'org.spigotmc:spigot-api:1.21.4-R0.1-SNAPSHOT'
    compileOnly files('libs/RPEngine.jar')
}
```

```kotlin
dependencies {
    compileOnly("org.spigotmc:spigot-api:1.21.4-R0.1-SNAPSHOT")
    compileOnly(files("libs/RPEngine.jar"))
}
```

</CodeTabs>

RP Engine runs on Java 17 and Minecraft 1.19.4 or newer, so target Java 17 if
you want your plugin to load everywhere the engine does.

In your `plugin.yml`, add `softdepend: [RPEngine]` so you load after it, or
`depend: [RPEngine]` if your plugin can't work without it.

## Getting in

Everything hangs off the plugin instance.

<CodeTabs labels={["Java", "Kotlin"]}>

```java
RPEnginePlugin engine =
    (RPEnginePlugin) Bukkit.getPluginManager().getPlugin("RPEngine");

engine.items();         // custom items
engine.models();        // models, and the ones standing in your worlds
engine.emotes();        // emotes and movement sets
engine.vehicles();      // vehicles, and the ones standing in your worlds
engine.shaderObjects(); // 3D shader objects: place them and drive them
engine.armor();         // 3D armour sets, and putting them on people
engine.sounds();        // custom sounds
engine.icons();         // icons, and putting one into text
engine.textEffects();   // Text Effects, and writing text in one
engine.vfx();           // VFX: play one where somebody stands
engine.overlays();      // HUD overlays: show one, hide one, feed it values
engine.dialogs();       // dialogs: open one, feed it values, read player settings
engine.registry();      // everything this server holds, by id
engine.registration();  // adding content of your own
```

```kotlin
val engine = Bukkit.getPluginManager().getPlugin("RPEngine") as RPEnginePlugin

engine.items()          // custom items
engine.models()         // models, and the ones standing in your worlds
engine.emotes()         // emotes and movement sets
engine.vehicles()       // vehicles, and the ones standing in your worlds
engine.shaderObjects()  // 3D shader objects: place them and drive them
engine.armor()          // 3D armour sets, and putting them on people
engine.sounds()         // custom sounds
engine.icons()          // icons, and putting one into text
engine.textEffects()    // Text Effects, and writing text in one
engine.vfx()            // VFX: play one where somebody stands
engine.overlays()       // HUD overlays: show one, hide one, feed it values
engine.dialogs()        // dialogs: open one, feed it values, read player settings
engine.registry()       // everything this server holds, by id
engine.registration()   // adding content of your own
```

</CodeTabs>

<Callout type="warning" title="What is API and what is not">
  Everything in `ai.resourcepack.engine.api` (and `api.event`) is supported.
  Nothing in `ai.resourcepack.engine.core` is, and it can change in any
  release, including a patch.
</Callout>

## IDs

Everything has one `namespace:path` ID, an ordinary Minecraft resource
location. `parse` returns empty rather than throwing, so a bad ID in somebody's
config becomes a message, not a stack trace.

<CodeTabs labels={["Java", "Kotlin"]}>

```java
ContentId ruby = ContentId.parse("mypack:ruby").orElseThrow();
```

```kotlin
val ruby = ContentId.parse("mypack:ruby").orElseThrow()
```

</CodeTabs>

**Store IDs, never what they resolve to.** An icon's codepoint moves when
content changes and an item's model is derived from its ID. The ID is the only
stable reference.

## Items

<CodeTabs labels={["Java", "Kotlin"]}>

```java
Optional<ItemStack> stack = engine.items().create(ruby);
Optional<ContentId> what  = engine.items().idOf(hand);
boolean isRuby            = engine.items().is(hand, ruby);
```

```kotlin
val stack: Optional<ItemStack> = engine.items().create(ruby)
val what: Optional<ContentId> = engine.items().idOf(hand)
val isRuby: Boolean = engine.items().`is`(hand, ruby)
```

</CodeTabs>

Identity lives in the stack's persistent data, not its name or model. An item
renamed in an anvil is still itself, and a vanilla diamond somebody named
"Ruby" is not one. `create` is main thread only; `ids()` and `info()` are safe
from any thread.

## Models

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.models().place(location, "golem", PlaceOptions.defaults());  // a Studio model
engine.models().place(location, tree, PlaceOptions.defaults().placer(player)); // an item's place: block
engine.models().itemFor("golem", ItemOptions.defaults());
engine.models().near(location, 16);   // what is standing around here
engine.models().at(entity);           // is this entity part of a model?
engine.models().at(entity).ifPresent(model -> model.play("wave", true)); // play on a placed model
```

```kotlin
engine.models().place(location, "golem", PlaceOptions.defaults())  // a Studio model
engine.models().place(location, tree, PlaceOptions.defaults().placer(player)) // an item's place: block
engine.models().itemFor("golem", ItemOptions.defaults())
engine.models().near(location, 16.0)  // what is standing around here
engine.models().at(entity)            // is this entity part of a model?
engine.models().at(entity).ifPresent { it.play("wave", true) } // play on a placed model
```

</CodeTabs>

Placing by item `ContentId` does exactly what a player placing that item does:
hitbox, seat, light, storage, states, animated rig and the item's `place`
actions. With a placer set, `ModelPlaceEvent` fires first. It returns empty
when the item has no `place:` block, the block is occupied, or a listener
cancelled it.

A `Placement` is a handle on a model standing in a world: `play` an animation,
`stop`, `remove(dropItem)`, read `playhead()` (how far into its animation it
is) and `seek(seconds)` to drive that clock yourself. `play(name, true)` starts
the animation over even if it is already running.

`bind` and `unbind` put a model on an entity that isn't ours, such as an NPC,
and `animate` plays on a model put on that way. **`animate` answers false for a
model standing in the world**, because nothing is wearing it. For one of those,
including the hitbox a right-click hands you, use `at(entity)` and `play` on the
placement, as above.

What a pack's `place:` block said is a read-only `ModelInfo`: facing, scale,
seat and light, plus `storage()` (a `StorageSpec`: type, rows, title, sounds),
`jukebox()`, `states()` with `nextState`, `lightIn` and `solidIn`, and
`grow()`. The engine handles the clicks itself; cancel `ModelInteractEvent` to
stop one. Growing fires neither `ModelBreakEvent` nor `ModelPlaceEvent`. See
[Working furniture](/rp-engine/furniture).

## Emotes

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.emotes().play(player, "wave");              // solo
engine.emotes().play(lead, "hug", List.of(other)); // with a cast
engine.emotes().canPerform(player);
engine.emotes().isEmoting(player.getUniqueId());
engine.emotes().stop(player);
```

```kotlin
engine.emotes().play(player, "wave")               // solo
engine.emotes().play(lead, "hug", listOf(other))   // with a cast
engine.emotes().canPerform(player)
engine.emotes().isEmoting(player.uniqueId)
engine.emotes().stop(player)
```

</CodeTabs>

<Callout type="warning" title="A cast is moved, so ask them first">
  An emote with a cast teleports the people it names. The engine's own `/emote`
  sends an invitation first; `play` does not, so asking is your job.
</Callout>

`EmoteResult` carries a typed reason rather than a sentence, so you write the
message in your own words and language.

### Putting a rig on somebody yourself

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.emotes().wear(player, "rowing");   // again to swap, null to take off
engine.emotes().face(player, 90f);        // point the body; null follows their look
engine.emotes().seek(player, seconds);    // pose the rig at this moment of its emote
engine.emotes().seekProp(player, "skate_right", clock); // drive one carried prop's clock
```

```kotlin
engine.emotes().wear(player, "rowing")    // again to swap, null to take off
engine.emotes().face(player, 90f)         // point the body; null follows their look
engine.emotes().seek(player, seconds)     // pose the rig at this moment of its emote
engine.emotes().seekProp(player, "skate_right", clock) // drive one carried prop's clock
```

</CodeTabs>

`wear` is a movement set where you, not the player's legs, decide what the rig
wears. Moving doesn't end it, and calling it again swaps without restarting.
`Emotes.BUILT_IN_SITTING` and `BUILT_IN_STANDING` work on any pack.

- `face` is for a passenger whose body belongs to a seat. Call it every tick
  with the seat's direction. It only affects a rig you put on with `wear`.
- `seek`, called every tick with a placement's `playhead()`, keeps a rig in
  step with a model's animation (a paddler's arms on a paddle).
- `seekProp` drives a carried prop by your own clock, such as a wheel that
  turns with distance travelled. It survives a swap to another emote carrying
  the same prop.

### Carrying a rig on a seat of your own

A worn rig follows its wearer by being teleported every tick, which the client
smooths out, so on anything fast it trails behind. Mount the rig's displays on
your seat instead and the client draws them wherever the seat is:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
int[] ids = engine.emotes().passengerEntityIds(rider);   // bones, carried models, hands
double lift = engine.emotes().rigOriginOffset();         // blocks above the feet
```

```kotlin
val ids = engine.emotes().passengerEntityIds(rider)      // bones, carried models, hands
val lift = engine.emotes().rigOriginOffset()             // blocks above the feet
```

</CodeTabs>

Every display hangs off one point, `rigOriginOffset()` above the rider's feet,
so put your seat's passenger position there. Read the number rather than
copying it, as it follows the size the engine draws players at.

<Callout type="warning" title="Mount with a packet, not addPassenger">
  The engine teleports every display every tick, and a Bukkit teleport of a
  passenger dismounts it. Send a client-side passengers packet instead. That
  packet is the vehicle's **whole** list: include whoever really sits there,
  resend it when the server sends its own, and send it to anybody who starts
  seeing the seat.
</Callout>

The ids change: putting a rig on spawns every display, and swapping to an emote
with different carried models spawns those again. `EmoteRigSpawnEvent` fires
each time with the new list, so mount there. It fires for every rig, so check
the player is yours.

### Rebuilding the rigs

A player's rig wears their skin, and rigs are baked into a pack. The engine
rebakes when a new skin arrives but only sends that build to whoever joins
next. To make everybody see everybody's current skin now (a minigame dressing
players in emotes), call `engine.reloadRigs()` on the main thread. On 1.20.3+,
where packs stack, that resends only the small rig pack and fires
`RigPackBuildEvent`; on older versions it is a full `reload()`.

## 3D armour

<CodeTabs labels={["Java", "Kotlin"]}>

```java
ContentId santa = ContentId.parse("christmas:santa").orElseThrow();

engine.armor().available();                           // false before 1.21.4
engine.armor().info(santa);                           // its name and pieces
engine.armor().create(santa, ArmorPiece.HELMET);      // one piece, as an item
ArmorResult result = engine.armor().wear(player, santa); // the whole set, now
engine.armor().wearing(player);                       // which set each worn piece is from
engine.armor().strip(player);                         // every 3D piece off
```

```kotlin
val santa = ContentId.parse("christmas:santa").orElseThrow()

engine.armor().available()                            // false before 1.21.4
engine.armor().info(santa)                            // its name and pieces
engine.armor().create(santa, ArmorPiece.HELMET)       // one piece, as an item
val result = engine.armor().wear(player, santa)       // the whole set, now
engine.armor().wearing(player)                        // which set each worn piece is from
engine.armor().strip(player)                          // every 3D piece off
```

</CodeTabs>

A set from a content folder is `namespace:path`; one pushed from Studio is
`studio:<id>`. Each piece is an ordinary item that goes on by hand like armour,
so `wear` is a shortcut for all four. Whatever was in a slot goes back to the
player (or drops at their feet if their inventory is full) and is listed in
`ArmorResult.displaced()`. `strip` removes only 3D pieces and gives them to
nobody. `ArmorResult` has a reason: `WORN`, `UNKNOWN_SET` or `UNSUPPORTED`.

A set pushed from Studio is only drawn for players holding that push's pack.
Main thread only, except `available`, `ids` and `info`. See
[3D armour](/rp-engine/armour).

## 3D shader objects

Needs RP Engine 0.2.10 or newer, and a server on Minecraft 1.21.4 or newer.
`engine.shaderObjects()` places and drives [3D objects](/rp-engine/objects):

<CodeTabs labels={["Java", "Kotlin"]}>

```java
ShaderObjects objects = engine.shaderObjects();
if (!objects.supported()) return;                     // false before 1.21.4
ContentId nuke = ContentId.parse("studio:nuke").orElseThrow();
ShaderObject bomb = objects.spawn(location, nuke).orElseThrow();

bomb.moveBy(new Vector(0, -20, 0), 50, Easing.IN);    // over 50 ticks
bomb.turnTo(90, 0, 0, 40, Easing.IN_OUT);             // yaw, pitch, roll
bomb.resize(40, 2, Easing.LINEAR);                    // diameter in blocks
bomb.state("detonate");                               // starts its clock
bomb.play("drop");                                    // a sequence from objects/
```

```kotlin
val objects = engine.shaderObjects()
if (!objects.supported()) return                      // false before 1.21.4
val nuke = ContentId.parse("studio:nuke").orElseThrow()
val bomb = objects.spawn(location, nuke).orElseThrow()

bomb.moveBy(Vector(0, -20, 0), 50, Easing.IN)         // over 50 ticks
bomb.turnTo(90f, 0f, 0f, 40, Easing.IN_OUT)           // yaw, pitch, roll
bomb.resize(40.0, 2, Easing.LINEAR)                   // diameter in blocks
bomb.state("detonate")                                // starts its clock
bomb.play("drop")                                     // a sequence from objects/
```

</CodeTabs>

`spawn(location, id, size)` sets the size; without it the object's own size is
used. `at(entity)`, `near(location, radius)` and `loaded()` find objects
already placed, and `ids()` and `info(id)` list what the server has (states,
sequences, size). On a handle, `replay()`, `settle()`, `seed(n)`, `moveTo`,
`stop()` and `remove()` match the [commands](/rp-engine/objects#commands);
`state(name)` and `play(name)` return false for a name the object doesn't have.
A time of 0 ticks is instant. Easing is `LINEAR`, `IN`, `OUT` or `IN_OUT`.

A handle lasts as long as its entity, and the object's state, place, turn and
size survive a restart; a running sequence or move does not. Main thread only,
except `ids` and `info`.

## Sounds

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.sounds().play(player, id);       // only this player hears it
engine.sounds().playAt(location, id);   // everybody nearby hears it here
engine.sounds().playFrom(entity, id);   // everybody nearby hears it follow this entity
```

```kotlin
engine.sounds().play(player, id)       // only this player hears it
engine.sounds().playAt(location, id)   // everybody nearby hears it here
engine.sounds().playFrom(entity, id)   // everybody nearby hears it follow this entity
```

</CodeTabs>

All three use the sound's declared category, volume and pitch, and each has an
overload that takes `volume` and `pitch`. Use `playFrom` for anything that
moves. Playing is main thread only; `ids()` and `info()` are safe from any
thread.

## HUD overlays

An overlay is a picture kept on a player's screen: a stat block, a health bar,
a crouch indicator. [Shader objects](/shaders) made in Studio are overlays, and
so are the ones in a [`huds/` folder](/rp-engine/hud). Server owners draw them;
your plugin decides who sees one and what numbers are in it.

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.overlays().show(player, "studio:health");  // stays until hidden
engine.overlays().hide(player, "studio:health");
engine.overlays().hideAll(player);
engine.overlays().showing(player);                // what they have on
```

```kotlin
engine.overlays().show(player, "studio:health")  // stays until hidden
engine.overlays().hide(player, "studio:health")
engine.overlays().hideAll(player)
engine.overlays().showing(player)                // what they have on
```

</CodeTabs>

An overlay made in Studio has the id `studio:<id>`, where `<id>` is the one on
its card on the pack page. There is no duration: to show one for five seconds,
schedule the `hide`.

### Feeding it values

An overlay's labels and progress bars can print `{name}` placeholders. Any name
works.

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.overlays().set(player, "stamina", "40");
engine.overlays().set(player, "stamina", null);   // remove it
engine.overlays().value(player, "stamina");       // what you last set
```

```kotlin
engine.overlays().set(player, "stamina", "40")
engine.overlays().set(player, "stamina", null)   // remove it
engine.overlays().value(player, "stamina")       // what you last set
```

</CodeTabs>

A placeholder is looked up in this order, and the first answer wins:

1. Whatever you `set`. A built-in with the same name never overrules it.
2. The built-ins: `player`, `name`, `displayname`, `uuid`, `world`, `x`, `y`,
   `z`, `direction`, `health`, `health_max`, `health_percent`, `food`, `air`,
   `level`, `xp`, `xp_points`, `xp_needed`, `ping`, `gamemode`, `online`,
   `max_online`, `time`, `day`. See [HUD overlays](/rp-engine/hud).
3. PlaceholderAPI, if the server has it.

A name none of them knows draws as nothing rather than as `{name}`.

Values are per player, not per overlay, and a progress bar reads the same
names, so a stamina bar out of 100 needs only the one `set` call. They are also
the values [dialogs](#dialogs) print.

The same values can change more than words. A piece of a Studio overlay can be
told, in its **From code** settings, to show only while a condition holds, to
switch to one of its named colours, or (a progress bar) to take its length or a
colour threshold from a value. Your plugin just sets the value:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.overlays().set(player, "status", "poisoned");  // a named colour
engine.overlays().set(player, "rank", "vip");         // Show when {rank} == "vip"
engine.overlays().set(player, "mana_len", "120");     // a bar 120 pixels long
```

```kotlin
engine.overlays().set(player, "status", "poisoned")  // a named colour
engine.overlays().set(player, "rank", "vip")         // Show when {rank} == "vip"
engine.overlays().set(player, "mana_len", "120")     // a bar 120 pixels long
```

</CodeTabs>

Colours can only be ones the overlay names, and shapes can't change at all:
they are compiled into the resource pack. See
[Changing it from code](/shaders#changing-it-from-code).

`set` and `value` are safe from any thread. They only record the value; the
next tick draws it, so six `set` calls in a row cost one redraw, and setting a
value to what it already was costs nothing. `show`, `hide` and `hideAll` are main thread only.

### Laying a value out

To build a line from several pieces (a kill feed: name, weapon icon, name), use
the engine's own measurements:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
int nameWidth = engine.overlays().width("Steve");  // pixels the cursor moves
String gap  = engine.overlays().space(5);          // five pixels of nothing
String back = engine.overlays().space(-12);        // twelve pixels back, to draw over
```

```kotlin
val nameWidth = engine.overlays().width("Steve")   // pixels the cursor moves
val gap = engine.overlays().space(5)               // five pixels of nothing
val back = engine.overlays().space(-12)            // twelve pixels back, to draw over
```

</CodeTabs>

`width` knows vanilla's letters, every icon in the pack and the spaces `space`
makes. Both work in any text drawn in the default font.

## Dialogs

A [dialog](/dialogs) is a screen of its own, such as a store, a settings menu
or a punish menu, on Minecraft 1.21.6 and newer. Server owners make them in
Studio or in a `dialogs/` folder; your plugin decides when one opens and what
values are on it.

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.dialogs().show(player, "studio:shop");
engine.dialogs().close(player);
engine.dialogs().ids();                        // what this server has
engine.dialogs().info(id);                     // name, command, settings it declares
engine.dialogs().supported();                  // false before 1.21.6
engine.dialogs().canShow(player, id);          // would show get as far as the client?
```

```kotlin
engine.dialogs().show(player, "studio:shop")
engine.dialogs().close(player)
engine.dialogs().ids()                         // what this server has
engine.dialogs().info(id)                      // name, command, settings it declares
engine.dialogs().supported()                   // false before 1.21.6
engine.dialogs().canShow(player, id)           // would show get as far as the client?
```

</CodeTabs>

A dialog made in Studio has the id `studio:<id>`, where `<id>` is the one in its
editor, and each page after the first is `studio:<id>.<page>`.

`show` returns false rather than throwing when the server is older than 1.21.6,
there is no such dialog, the player is offline, or they don't hold the pack the
dialog's picture is in. `canShow` checks all of that first. What it can't
promise is that the game accepts the dialog's JSON; a refusal is logged to the
console.

A dialog can declare a command players open it with (`/shop`). The engine
registers it; `DialogInfo.command()` and `permission()` say what it is.
`DialogInfo.quickAction()` says whether it is on the [Quick Actions
key](/dialogs#the-quick-actions-key) (G).

A dialog opens straight away even if it was pushed a moment ago, because the
engine sends the whole dialog. `pending()` only tells you whether its id is in
the server's registry yet, which matters only to a datapack or command block of
your own that names it.

### Values on it

A dialog's words can print `{name}` placeholders, on its screen as well as in
its title, tooltips, buttons and commands. See [Live values](/dialogs#live-values).
Hand values over as you open it:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.dialogs().show(staff, "studio:punish", Map.of("target", suspect.getName()));
// "Punish {target}" opens as "Punish Steve", the name and the face on its card are Steve's,
// and a reason that runs "mute {target} 1h" runs "mute Steve 1h".
```

```kotlin
engine.dialogs().show(staff, "studio:punish", mapOf("target" to suspect.name))
// "Punish {target}" opens as "Punish Steve", the name and the face on its card are Steve's,
// and a reason that runs "mute {target} 1h" runs "mute Steve 1h".
```

</CodeTabs>

Or publish a value once, for every dialog and HUD that prints it. These are the
same values `overlays().set` publishes, one set per player:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.dialogs().set(player, "coins", String.valueOf(balance));
engine.dialogs().set(player, "coins", null);    // remove it
engine.dialogs().value(player, "coins");        // what you last set
```

```kotlin
engine.dialogs().set(player, "coins", balance.toString())
engine.dialogs().set(player, "coins", null)     // remove it
engine.dialogs().value(player, "coins")         // what you last set
```

</CodeTabs>

A [list](/dialogs#lists-the-server-fills) (rows drawn in Studio, one per item)
is filled all at once:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.dialogs().list(player, "warps", List.of("Spawn", "Shop", "Arena"));
// More than one field a row: "" is the row's own value, "note" is {warps_note}.
engine.dialogs().listRows(player, "warps", List.of(Map.of("", "Spawn", "note", "Where you start")));
```

```kotlin
engine.dialogs().list(player, "warps", listOf("Spawn", "Shop", "Arena"))
// More than one field a row: "" is the row's own value, "note" is {warps_note}.
engine.dialogs().listRows(player, "warps", listOf(mapOf("" to "Spawn", "note" to "Where you start")))
```

</CodeTabs>

It sets `warps_1`, `warps_2` and so on plus `warps_count`, and clears items a
longer list set before. Rows past the end are hidden, clicks and all. The
command that opens a dialog can pass a list too, `warps=Spawn,Shop,Arena`, for
that opening only.

A placeholder is looked up in this order, and the first answer wins:

1. What you passed to `show` (case-insensitive).
2. What you published with `set` (or `overlays().set`).
3. The built-ins, the same ones a HUD has, all about the player viewing it.
4. PlaceholderAPI, if the server has it.
5. The player's own [settings](#player-settings).

Settings come last because players change them themselves with a command. A
setting can never stand in for a real value, but a setting that shares a name
with anything above shows that value instead, so give settings names of their
own.

A name nothing answers is left as written, so a dialog that says `{VIP}` stays
as it is. Formatting codes are removed from values. On a Studio dialog's
screen, a value is limited to characters the game's small font draws (others
become `?`) and is cut short with "…" if it doesn't fit its line.

**A dialog is drawn once, as it opens.** A value that changes while it is on
screen shows next time. Call `reopen` after a click changed something; it opens
the dialog again with the values it was opened with:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
// A Buy button on the store runs /buy sword. In your command:
economy.withdraw(player, price);
engine.dialogs().set(player, "coins", String.valueOf(economy.getBalance(player)));
engine.dialogs().reopen(player);   // the store again, with the new balance on it
```

```kotlin

economy.withdraw(player, price)
engine.dialogs().set(player, "coins", economy.getBalance(player).toString())
engine.dialogs().reopen(player)    // the store again, with the new balance on it
```

</CodeTabs>

The server isn't told when a player closes a dialog, so `reopen` opens it
whether it is still on screen or not. Call it in answer to a click, not on a
timer.

### Player settings

A switch, slider or choice on a Studio dialog can be bound to a [player

| | |
| --- | --- |

### Your own container in a dialog

A Studio dialog can have a grid of item slots showing a container "from a
plugin", by name. Register one under that name and the grid shows your
inventory for whoever opens it, and lets them move items in and out where the
grid allows it:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
engine.dialogs().container("bank", new DialogContainer() {

    public Inventory inventory(Player viewer) {
        return banks.of(viewer);

    public boolean mayPlace(Player viewer, int slot, ItemStack stack) {

    }

    @Override
    public void changed(Player viewer) {
```

The engine reads your inventory as each dialog opens and writes to it as each

### Fuel, and anything else that stops a vehicle going

`setEnabled(false)` is the switch. A disabled vehicle ignores its driver and
coasts to a halt, still falls and floats, and people get in and out as normal.
The flag is saved on the chassis, so a car that ran dry is still dry after a
restart.

<CodeTabs labels={["Java", "Kotlin"]}>

```java
NamespacedKey fuel = car.key(this, "fuel");

@EventHandler
public void onState(VehicleStateEvent event) {
    // Burn only while it is actually going somewhere.
    if (event.entered(VehicleState.MOVING)) burners.add(event.vehicle());
    if (event.left(VehicleState.MOVING)) burners.remove(event.vehicle());
}

// once a second
for (Vehicle vehicle : burners) {
    int left = vehicle.data().getOrDefault(fuel, PersistentDataType.INTEGER, 0) - 1;
    vehicle.data().set(fuel, PersistentDataType.INTEGER, Math.max(0, left));
    vehicle.setEnabled(left > 0);
}
```

```kotlin
val fuel = car.key(this, "fuel")

@EventHandler
fun onState(event: VehicleStateEvent) {
    // Burn only while it is actually going somewhere.
    if (event.entered(VehicleState.MOVING)) burners += event.vehicle()
    if (event.left(VehicleState.MOVING)) burners -= event.vehicle()
}

// once a second
for (vehicle in burners) {
    val left = vehicle.data().getOrDefault(fuel, PersistentDataType.INTEGER, 0) - 1
    vehicle.data().set(fuel, PersistentDataType.INTEGER, maxOf(0, left))
    vehicle.setEnabled(left > 0)
}
```

</CodeTabs>

`data()` is the chassis's persistent data and survives everything the vehicle
does. `uniqueId()` is the chassis's id and the one stable key: seats and model
entities get new ids on every chunk load, so never store those.

| Method | What it does | Saved? |
| --- | --- | --- |
| `setEnabled(boolean)` | Ignores the driver and coasts to a halt | Yes |
| `setSpeedLimit(bps)` | Lower top speed, braking and reverse scaled to match. An aircraft limited below takeoff speed can't take off | No |
| `setHandling(speed, turn)` | Scales what it can do, as fractions of its definition | No |
| `setDamage(VehicleDamage)` | Per-wheel condition, engine power and steering pull, read by the handling model | No |
| `setDescent(bps)` | An aircraft comes down at this rate whatever it's doing. 0 holds height, negative clears it | No |
| `setPosture(pitch, roll)` | A drawn lean on top of the physics | No |
| `stop()` | Dead this tick, like hitting a wall | |

Re-apply the unsaved ones when you pick a vehicle up again (after a chunk load
or restart). `VehicleDamage.NONE` is the vehicle exactly as its pack defines
it:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
car.setDamage(VehicleDamage.builder()
        .wheel(VehicleCorner.FRONT_LEFT, 0)     // torn off
        .wheel(VehicleCorner.REAR_LEFT, 0.45)   // buckled
        .enginePower(0.7)
        .steeringPull(-3)                       // pulls left
        .build());
```

```kotlin
car.setDamage(VehicleDamage.builder()
        .wheel(VehicleCorner.FRONT_LEFT, 0.0)   // torn off
        .wheel(VehicleCorner.REAR_LEFT, 0.45)   // buckled
        .enginePower(0.7)
        .steeringPull(-3.0)                     // pulls left
        .build())
```

</CodeTabs>

A wheel runs from 1 (sound) to 0 (gone). Damage is not health and never
changes the art; the engine has no opinion on how much punishment a vehicle
takes. That is yours to track in `data()`.

<Callout type="note" title="Who may get in is an event, not a method">
  There is no `setLocked`. Cancel `VehicleEnterEvent` and they stay standing.
  `VehicleExitEvent` can't be cancelled, so a player is never trapped; to keep
  somebody in a race, put them back with `seat`.
</Callout>

### Collisions and parts

`VehicleImpactEvent` fires once per meaningful collision (`cause()`: `VEHICLE`,
`WORLD` or `LANDING`). `first()` and, for a vehicle pair, `second()` each carry
the velocity before and the change, the contact normal, closing speed, impulse,
spin change, `area()` (which side took it) and `contactOffset()` (where on the
vehicle, in its own frame: `x` right, `y` up from its base, `z` forward). A zero
offset means the engine can't say where. For `WORLD` impacts it is a face, not a
point.

To react:

- `applyImpulse(deltaVelocity, spinDelta)` changes the physical response;
  `velocity()` reads it.
- `scuff(area, contact, amount)` adds a persistent scrape (amount 0 to 1, at
  most ten marks; a repeat hit in the same place deepens the mark).
- `parts()` lists an animated model's bones, `partOffset(name)` says where one
  sits, and `detachPart(name, velocity, spin, despawnTicks)` knocks it off.
  `detachedParts()` is saved on the chassis.
- `showStatus(text)` borrows the vehicle's action-bar line for a moment.

### Building a vehicle the engine does not have

A skateboard is pushed rather than throttled, tucks for speed and spins in the
air. None of that is in the format, but the handle exposes the pieces:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
Vehicle board = engine.vehicles().of(player).orElseThrow();
VehicleInput keys = board.input();          // what the driver is pressing, this tick
if (keys.forward() && board.groundSpeed() < 7) {
    board.nudge(2.2);                       // a kick: +2.2 blocks/s along the heading
    board.dress(player, "myplugin_push");   // wear this emote over the seat's states
}
if (board.is(VehicleState.AIRBORNE) && keys.left()) board.spin(-360);
board.undress(player);                      // back to the seat's own table
board.dressVariant(player, "goofy");        // this rider's own variant of every state
board.turnOccupant(player, 270.0);          // face a different way from the seat; null resets
board.holdOccupant(player, true);           // sneak no longer dismounts while moving
board.wallRiding();                         // is it on a wall right now?
```

```kotlin
val board = engine.vehicles().of(player).orElseThrow()
val keys = board.input()                    // what the driver is pressing, this tick
if (keys.forward() && board.groundSpeed() < 7) {
    board.nudge(2.2)                        // a kick: +2.2 blocks/s along the heading
    board.dress(player, "myplugin_push")    // wear this emote over the seat's states
}
if (board.`is`(VehicleState.AIRBORNE) && keys.left()) board.spin(-360.0)
board.undress(player)                       // back to the seat's own table
board.dressVariant(player, "goofy")         // this rider's own variant of every state
board.turnOccupant(player, 270.0)           // face a different way from the seat; null resets
board.holdOccupant(player, true)            // sneak no longer dismounts while moving
board.wallRiding()                          // is it on a wall right now?
```

</CodeTabs>

- `input()` is the same input the physics read, on the same tick. Where keys
  can't be read (Spigot, or before 1.21.4) `keys()` is false and only
  `throttle()` means anything. Nothing in the engine acts on sprint, so it's
  yours to use.
- `dressVariant` turns `moving` into `moving_goofy` and so on, falling back to
  the plain emote where no variant exists.
- **Sneak is Minecraft's dismount.** Call `holdOccupant` once, when they get
  on: the dismount happens before your next tick task could react. A held rider
  can still get off by tapping sneak, and the hold stops applying once the
  vehicle is below half a block a second, so nobody is ever trapped. Tell
  riders what the key does now.

### Moving the vehicle's own model

`dress` is for the rider. `perform` plays one of the **model's** animations
instead of whatever its `animations:` table says:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
bike.perform("wheelie");   // the whole bike tips back about the rear axle
// ... count your ticks ...
bike.rest();               // back to the state table, wheels where they were
```

```kotlin
bike.perform("wheelie")    // the whole bike tips back about the rear axle
// ... count your ticks ...
bike.rest()                // back to the state table, wheels where they were
```

</CodeTabs>

It works on a vehicle with no `animations:` at all. A performed animation loops
until you call `rest()`, so you time the trick. It runs on real time even on a
vehicle with
[`animation-follows-speed`](/rp-engine/vehicles#a-wheel-should-turn-because-the-vehicle-moved),
and the wheels pick up where they were afterwards. One animation plays at a
time, so a trick that needs the wheels turning must turn them itself.

Every vehicle handle method is main thread only. `ids`, `info` and `isRiding`
are safe anywhere.

## Text Effects in your own text

A [Text Effect](/rp-engine/text-effects) is a colour: text drawn in exactly

<CodeTabs labels={["Java", "Kotlin"]}>

```java
TextEffects effects = engine.textEffects();

player.sendMessage(effects.format(config.getString("welcome"))); // "Welcome to <fx:rainbow>Skyblock</fx>!"

// One effect by name: a content folder's before a Studio one.
effects.find("fire").ifPresent(fire -> {
    meta.setDisplayName(effects.apply(fire.id(), "Flame Sword"));
```


| Method | What it does |
|---|---|
| `ids()` | Every Text Effect, both sources, sorted |
| `info(id)` | A `TextEffectInfo`, by ID |
| `find(name)` | By what somebody typed: `mypack:fire`, or a bare `fire` |

## VFX

A [VFX](/rp-engine/vfx) is a spell effect the engine plays in the world. Play
one at a place, or on a player (at their feet, facing their way), and keep the
handle if you want to end it early.

<CodeTabs labels={["Java", "Kotlin"]}>

```java
Vfx vfx = engine.vfx();

vfx.find("frost_nova").ifPresent(info -> {
    vfx.play(info.id(), player).ifPresent(play -> {
        // play.running() until it ends; play.stop() ends it now.
    });
});
```

```kotlin
val vfx = engine.vfx()

vfx.find("frost_nova").ifPresent { info ->
    vfx.play(info.id(), player).ifPresent { play ->
        // play.running() until it ends; play.stop() ends it now.
    }
}
```

</CodeTabs>

| Method | What it does |
|---|---|
| `ids()` | Every VFX, both sources, sorted |
| `info(id)` | A `VfxInfo`, by ID |
| `find(name)` | By what somebody typed: `mypack:frost`, or a bare `frost` |
| `play(id, location)` | Plays it there, facing the location's yaw. Empty for an unknown ID, or below 1.21.4 |
| `play(id, player)` | Plays it where the player stands, facing their way |
| `play(id, location, caster, options)` | Plays it as a `VfxOptions` says (below); `caster` is whose placeholders a condition reads, and may be null |
| `play(id, player, options)` | The same, cast on a player |
| `playing()` | Every `VfxPlay` playing now |
| `stop(tag)` / `stop(player)` | Ends the effects with that tag, or cast on that player, and says how many |
| `stopAll()` | Ends them all, and says how many there were |

`VfxOptions` is every [casting option](/rp-engine/vfx#casting-options):
`loop()`, `loopFor(ticks)`, `loopTimes(n)`, `until(condition)`,
`whileTrue(condition)`, `stopWhen(play -> ...)` (a check of your own, run every
`checkEvery(ticks)`), `end(End.FINISH | End.CUT)`, `speed`, `scale`, `turn`,
`offset(left, up, ahead)`, `follow(entity)`, `delay`, `vary`, `seed`, `sounds`,
`volume`, `viewers(Viewers.EVERYONE | Viewers.CASTER)` and `tag`.

```java
vfx.play(id, player, VfxOptions.builder()
        .loop()
        .stopWhen(play -> !combat.isFighting(player))
        .follow(player)
        .tag("combat-aura")
        .build());
```

`VfxInfo` has `id()`, `name()`, `durationTicks()`, `source()` (`CONTENT` or
`STUDIO`) and `preset()`. A `VfxPlay` has `id()`, `location()`, `running()`,
`stop()` (now), `finish()` (a loop plays out its fade), `options()`, `age()`
and `passes()`. A Studio VFX is shown only to the players whose pack has it. Main
thread only.

## Events

All in `ai.resourcepack.engine.api.event`, and cancellable unless the row says
otherwise.

| Event | When |
|---|---|
| `ContentLoadEvent` | Content finished loading and the packs are built. A reload replaces every definition, so rebuild anything you cached here. `cause()` is `STARTUP` or a reload. Not cancellable |
| `PackSendEvent` | A pack went out to a player. `pack()` is the built pack; its `uuid()` is the id `PlayerResourcePackStatusEvent` reports on 1.20.3+, so you can match the two. Not cancellable |
| `RigPackBuildEvent` | The emote rigs were rebaked: on every content load, or alone for a new skin or `reloadRigs()`. `alone()` and `separate()` say which. Not cancellable |
| `ItemUseEvent` | A custom item was right- or left-clicked. `block()` and `face()` say what was clicked (null in the air). Cancelling cancels the vanilla use too |
| `ModelPlaceEvent` | A model is about to be put down. `stack()` is the stack in the player's hand it's placed from, so you can read what the item carries; null when a plugin placed it |
| `ModelPlacedEvent` | A model was put down and is standing. `placement()` is its handle and `stack()` the stack it came from, so you can copy what the item carries onto the placement's `data()`. Not cancellable |
| `ModelBreakEvent` | A model is about to be broken. `hitbox()` is its Interaction entity (its UUID tells two copies of one model apart) and `placement()` its handle. Has a drop flag separate from cancelling |
| `ModelInteractEvent` | A placed model was right-clicked, from your content folder or from Studio. Has `hitbox()`, `placement()` and `clickedPosition()`. Cancelling stops everything the engine would do with the click |
| `ModelAnimationEvent` | A model is about to play an animation |
| `ModelAnimationEndEvent` | One ended: finished, replaced or stopped. Not cancellable |
| `ModelSeatEvent` | Somebody is about to sit on a chair, a seat bone or a vehicle seat. `placement()` or `vehicle()` says what it belongs to |
| `ModelBindEvent` | A model is going on, or coming off, an entity that isn't ours (a boss, an NPC) |
| `VehicleEnterEvent` | Somebody is about to get into a vehicle. Fires after `ModelSeatEvent` for the same seat |
| `VehicleExitEvent` | Somebody got out or was taken out, with the reason: dismounted, ejected, quit, reloaded, removed, unloaded, shutdown. After `RELOADED` they're put back a tick later with no enter event. Not cancellable |
| `VehicleMoveEvent` | A vehicle is about to move (once per tick, only while moving). Cancelling stops it like a wall. Use it for regions, not fuel |
| `VehicleStateEvent` | What a vehicle is doing changed: set off, stopped, took off, went under. Not cancellable |
| `VehicleImpactEvent` | A vehicle hit another vehicle, the world, or the ground. See [Collisions and parts](#collisions-and-parts). Not cancellable |
| `VehicleBailEvent` | A bad landing is about to throw a rider off. Cancelling keeps them aboard |
| `EntityDeathEvent` | A custom entity died. Says what it was, `killer()`, and `drops()`: Bukkit's live drop list, so editing it changes the loot. Not cancellable |
| `PlayerLiquidEvent` | Somebody went into or came out of one of your liquids. Not cancellable |
| `EmoteStartEvent` | An emote is about to start |
| `EmoteEndEvent` | An emote ended, with the reason: finished, stopped, moved, damaged, quit, shutdown |
| `EmoteRigSpawnEvent` | A rig's displays were spawned. Carries the new entity ids. Not cancellable |
| `DialogSlotMoveEvent` | A player is about to move a stack in a dialog's item slots, from one slot (`inv/5`, `ender/3`, `api.bank/0`) to another |

**The engine decides whether something can physically happen, never whether it
is allowed to.** Region protection, plot ownership and event worlds are rules
about your server, and these events are where you enforce them.

<CodeTabs labels={["Java", "Kotlin"]}>

```java
@EventHandler
public void onPlace(ModelPlaceEvent event) {
    if (!myRegions.mayBuild(event.getPlayer(), event.block())) {
        event.setCancelled(true);
    }
}

@EventHandler
public void onLoad(ContentLoadEvent event) {
    menus.rebuild();
}
```

```kotlin
@EventHandler
fun onPlace(event: ModelPlaceEvent) {
    if (!myRegions.mayBuild(event.player, event.block())) {
        event.isCancelled = true
    }
}

@EventHandler
fun onLoad(event: ContentLoadEvent) {

}
```

</CodeTabs>

<Callout type="warning" title="A plugin loading after RP Engine misses the first load">
  The `STARTUP` event has already fired before your listener exists. Don't work
  around it with a delayed task: query the API in your own `onEnable`, and use
  the event for reloads after that.
</Callout>

### Priority

The engine reads every one of these events after all handlers have run, so
priority only orders you against other plugins. Listen at `NORMAL` unless you
are deliberately arbitrating with another plugin, and treat `MONITOR` as
read-only (a cancel there still counts).

Vanilla's own events are different. The engine listens to those at `LOW` with
`ignoreCancelled = true`, so cancelling a `PlayerInteractEvent` at `LOWEST`
stops a custom item's use before RP Engine sees the click, which is usually
what a protection plugin wants.

## Shipping content in your own jar

An addon carries its models, items, vehicles and emotes as an ordinary
[content folder](/rp-engine/content) inside its jar, under
`resources/content/<namespace>/`, and installs it on enable:

<CodeTabs labels={["Java", "Kotlin"]}>

```java
try {
    if (AddonContent.install(this, engine, "skateboards")) {
        engine.reload();   // only when something actually changed
    }
} catch (IOException e) {
    getLogger().severe("Could not install content: " + e.getMessage());
    getServer().getPluginManager().disablePlugin(this);
}
```

```kotlin
try {
    if (AddonContent.install(this, engine, "skateboards")) {
        engine.reload()    // only when something actually changed
    }
} catch (e: IOException) {
    logger.severe("Could not install content: ${e.message}")
    server.pluginManager.disablePlugin(this)
}
```

</CodeTabs>

It copies into `plugins/RPEngine/content/<namespace>/` and returns true only
when something changed, so restarting on the same jar copies and reloads
nothing. A reload rebuilds and resends every pack, so don't call it otherwise.

A new build updates its own files and leaves everything else alone. If the
server owner edited one of your shipped files, that edit survives the update:
the console names the file and says to delete it to take the new version. Use
your plugin's name as the namespace, and put RP Engine in `depend`.

## Registering content from code

A plugin can add content directly instead of shipping a folder. Claim a
namespace, define into the handle you get back, and the pack builder picks it
up on the next build.

<CodeTabs labels={["Java", "Kotlin"]}>

```java
ClaimResult claim = engine.registration()
        .claim("myplugin", ContentSource.EMBEDDED);

claim.namespace().ifPresent(ns -> {
    ns.define(ContentKind.ITEM, "ruby");
    // ... and ns.release() when your plugin disables
});
```

```kotlin
val claim = engine.registration()
    .claim("myplugin", ContentSource.EMBEDDED)

claim.namespace().ifPresent { ns ->
    ns.define(ContentKind.ITEM, "ruby")
    // ... and ns.release() when your plugin disables
}
```

</CodeTabs>

If the claim fails, `reason()` says why and `heldBy()` who has it. Holding
`myplugin` can't define `otherpack:thing`, so two sources can't overwrite each
other. `release()` drops the namespace and everything in it. Content from a
plugin goes into the same registry under the same rules as a hand-written
folder.

## Threading

Reads about what the server holds (`ids`, `info`, all of `ContentRegistry`)
are safe from any thread. Anything touching a player, an entity or a world is
main thread only, and its javadoc says so.

**On Folia there is no main thread**, so "main thread" means the thread that
owns what the call touches: the player's or entity's own scheduler for
anything about them (`player.getScheduler().run(...)`), and the region
scheduler for anything at a place (`Bukkit.getRegionScheduler().run(plugin,
location, ...)`), such as placing a model or playing a VFX at a spot. A call
from the global region or another region's thread is the same mistake a call
from an async thread is on Paper. Everything RP Engine does on its own already
follows this, so your plugin only has to for the calls it makes.
