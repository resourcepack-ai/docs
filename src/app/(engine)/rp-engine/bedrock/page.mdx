# Bedrock and Geyser

RP Engine hooks into [Geyser](https://geysermc.org/) to hand Bedrock players a
pack of their own, so they see your custom items with your art rather than the
plain vanilla item underneath.

If **Geyser-Spigot** is on the server, the engine builds a Bedrock `.mcpack`
from your content every time it builds the Java pack, and serves it to every
Bedrock player as they join. There is nothing to configure; it is detected and
used. The console says what went into it:

```
[RPEngine] Bedrock pack built: 12 items, 4 sounds, 6 icons, 2 armour pieces.
```

It is built from your default bundle (`default-bundle` in `config.yml`), since
that is the one every player is given. It lands beside the Java zip in
`plugins/RPEngine/output/`.

## What crosses over

- **Items with a flat sprite.** A Bedrock player sees the item with your art
  and its name. A [3D item](/rp-engine/items#3d-items) crosses only if it also
  has a sprite at its `texture:` path, which Bedrock uses as its icon: Bedrock
  cannot draw a Java model in a hand.
- **Armour** on those items, on the body, from the same equipment texture.
- **Sounds.** A sound plays on Bedrock under the same id it plays under on
  Java, so actions and commands that play `mypack:laser` work for everyone.
- **Icons**, in chat and anywhere else text goes. Every icon is drawn about a
  line of text tall on Bedrock, whatever its height on Java.

## What does not

**Placed models from your content folder.** Geyser does not draw the display
entities a placed model is made of, so a Bedrock player sees the hitbox and
nothing else.

<Callout type="note" title="Models from Studio are the exception">
  A model pushed or distributed from Studio carries a Bedrock copy of itself,
  and the engine draws it for Bedrock players as a native entity, animations
  included. See [Studio models on Bedrock](#studio-models-on-bedrock).
</Callout>

**Emotes and vehicles**, for the same reason: both are rigs of display
entities.

**Custom screens, HUD overlays and dialogs.** All three are drawn through the
Java font or the Java dialog system, and Bedrock has neither.

**3D armour.** It is drawn by display entities or by a Java shader, and
Bedrock players see neither.

**Replacing a vanilla sound.** A file in `overrides/` that replaces a vanilla
sound changes it on Java only: Geyser turns vanilla sounds into Bedrock's own
before the pack is asked.

## New items need a restart

Geyser learns which Java items are custom **once, at startup**. `/rp reload`
rebuilds the Bedrock pack and every Bedrock player gets the new art on their
next join, but an item that did not exist at startup shows as its base
material to Bedrock players until the server restarts. The console says so when
it happens.

## Studio models on Bedrock

A pack pushed from Studio with `/rp sync`, or served through Studio's
distribution, includes a Bedrock build when any player receiving it is on
Bedrock. The engine hands that build to them the only way Bedrock allows: a
Bedrock client takes packs only while joining, so it is transferred back to the
same server and served the pack on the way in. It takes a few seconds and the
sync survives it.

Placed Studio models then show up for Bedrock players as native entities, drawn
when a player comes within 48 blocks and removed when they leave. Their
animations play on the player's own client from the pack's keyframes, started
by the same triggers as on Java.

## Designing for both

The rule that works: **make the item carry the meaning, and the model carry the
delight.** A key that is obviously a key on Bedrock is fine if it is also a
beautiful 3D key on Java; a puzzle whose only clue is a placed model is a
puzzle Bedrock players cannot see.

If your server is Java-first and Bedrock is a bonus, none of this matters much.
If Bedrock is a real part of your player base, it is worth knowing which of
your content is decoration and which is information.
