# MCP server

ResourcePack AI speaks the **Model Context Protocol**, so an AI agent can build
a pack for you: create it, generate blocks, models, items, GUIs, dialogs, icons
and sounds, bring in files you already have, look at what came back, and try
again where it's wrong.

It is the same API as the rest of this reference, with the same AI Credits and
a key of its own. The difference is that an agent gets a list of tools to call
instead of URLs it has to be programmed against.

<Callout type="note" title="On every plan">
  MCP keys are available on every plan, the free one included, and the MCP
  server spends the same AI Credits Studio does. There is no separate MCP pricing.
</Callout>

## Connect

The server lives at **`https://api.resourcepack.ai/mcp`** and authenticates with
an **MCP key** from the [Developers page](https://studio.resourcepack.ai/developers).
MCP keys start `rpai_mcp_` and only work on the MCP server, and API keys only
work on the REST API, so revoking the key you gave an agent never breaks your
own code. The wrong kind of key is refused with `wrong_key_kind`. (Keys made
before MCP keys existed work in both places.)

<Steps>
  <Step title="Get an MCP key">
    [studio.resourcepack.ai/developers](https://studio.resourcepack.ai/developers),
    the **MCP keys** card. Copy it straight away: it is only shown once.
  </Step>
  <Step title="Add the server to your client">
    In Claude Code:

    ```bash
    claude mcp add --transport http resourcepack-ai \
      https://api.resourcepack.ai/mcp \
      --header "Authorization: Bearer rpai_mcp_YOUR_KEY"
    ```

    Any client that takes a JSON config wants this:

    ```json
    {
      "mcpServers": {
        "resourcepack-ai": {
          "type": "http",
          "url": "https://api.resourcepack.ai/mcp",
          "headers": { "Authorization": "Bearer rpai_mcp_YOUR_KEY" }
        }
      }
    }
    ```
  </Step>
  <Step title="Ask for something">
    "Make me a pack of overgrown temple blocks: mossy bricks, cracked stone and
    a carved idol model." The agent will create the pack, generate into it, wait
    for the results and show you what it made.
  </Step>
</Steps>

<Callout type="warning" title="A key is your whole account">
  It can read, generate into and export every pack you own or collaborate on,
  and it spends your credits. An agent you connect it to can do all of that
  without asking. Use a key created for the purpose so you can revoke it on its
  own, and keep an eye on [its history](/api-reference/history).
</Callout>

The tools are generated from the same source as this reference and the
[OpenAPI document](/openapi.json), so they take the same arguments, limits and
enums. An endpoint that is switched off is left out of the list.

### `wait_for_job` waits, so the agent doesn't poll

Every generation is [asynchronous](/api-reference/jobs): you get a job handle
and poll it. For an agent, each poll costs a whole turn, so `wait_for_job` does
the waiting on the server instead. The agent passes every handle it is waiting
on in one call and gets one answer when they have all finished.

It waits 120 seconds by default, up to 600 with `timeoutSeconds`. If time runs
out it says which jobs are still going and the agent calls again. Nothing is
lost or charged twice.

### Files come back as files

`get_asset_file` returns a generated texture, sprite or icon **as an image**, so
the agent can actually look at what it made before telling you it is done, and
regenerate it if it is wrong. Sounds come back as audio, models as their JSON.

### Sending files in

`upload_asset`, `upload_reference` and `import_pack` take a `file` in one of
four forms:

- **`text`**: the file as text, such as a model's JSON the agent wrote itself.
- **`base64`**: the bytes inline. Fine for a 16px texture.
- **`url`**: a public `https` address to fetch it from.
- **`upload`**: the id from `create_upload`, after the bytes were PUT to the URL it returned.

Use `upload` for any file on disk. An agent with a shell sends the bytes
itself, so they never pass through the model:

```bash
curl -T lantern.bbmodel "<url from create_upload>"
```

Base64 works too, but an agent writes it a token at a time, so it is slow and
expensive for anything bigger than a small image.

An import runs after `import_pack` answers, like a generation: the agent waits on
its job (`<pack>:import`) with `wait_for_job`, and `get_job` then has the full
report of what came in and what was left out.

`export_pack` confirms the export built and how big it is, but doesn't return the
file, which is megabytes an agent has no use for. Download it over HTTP with an
**API** key (an MCP key is refused there):

```bash
curl -H "Authorization: Bearer $RPAI_KEY" -o pack.zip \
  https://api.resourcepack.ai/v1/packs/YOUR_PACK/export
```

## Limits and behaviour

| | |
| --- | --- |
| **Transport** | Streamable HTTP. POST JSON-RPC. The server doesn't open a message stream, so a `GET` answers 405. |
| **Sessions** | None. Every request carries the key and stands alone, so a dropped connection costs nothing. |
| **Rate limits** | The same budgets as the REST API: [120 reads and 30 writes a minute](/api-reference/rate-limits) per key. `wait_for_job` paces its own polling to stay inside the read budget. |
| **Errors** | A failed call comes back as a tool error the agent can read and act on, carrying the same [stable code](/api-reference/errors) the REST API uses. |
| **Origin check** | The two [origin-check endpoints](/api-reference/origin) are not tools. They need no key and exist for marketplaces, who are better served over HTTP. |

<Callout type="tip" title="Tell it what you want, not how">
  The server gives the agent its own briefing (what a pack is, that generating
  costs credits, how to tell assets apart by `type`), so you don't have to
  explain any of it. Describe the pack you want and let it choose the calls.
</Callout>
