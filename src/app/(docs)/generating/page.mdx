# Generating with AI

Generation exists to get you past the blank grid. What comes back won't
always be perfect, and that's fine: the editors are there for the finishing
touches.

## Where it lives

Everything starts from **Add asset** on the pack page. First you choose how to
start (**Generate**, **Draw** or **Upload**), then what you're making, and
the fields underneath change with the type: which vanilla block or item you're
replacing, a resolution for pixel art, a quality tier for a model, an event
name for a sound.

Not every type is behind every option:

| | Generate | Draw | Upload |
| --- | --- | --- | --- |
| **Block** | ✓ | ✓ | ✓ |
| **Model** | ✓ | ✓ | ✓ (`.bbmodel`) |
| **Item** | ✓ | ✓ | ✕ |
| **GUI** | ✕ | ✓ | ✕ |
| **Icon** | ✓ | ✓ | ✓ |
| **Sound** | ✓ | ✕ | ✕ |

**GUIs can't be generated yet**: the AI isn't capable of drawing a good
screen, and we're working on it. And **sounds are only generated**, since
there's nothing to draw.

## What each kind comes back as

<Steps>
  <Step title="Blocks and items">
    Drawn as **pixel-art-native images at the resolution you picked**, so a
    32×32 texture is really drawn at 32 rather than scaled up from something
    smaller. Seconds per image. See [Blocks](/blocks) and
    [Items](/items).
  </Step>
  <Step title="Models">
    Built rather than conjured, by one engine: **the builder**, a reasoning AI
    working through real building tools. It plans the model, places named
    parts, groups them into bones with pivots at the joints, paints the
    material textures for the faces (or points them at vanilla textures like
    `minecraft:block/iron_block` directly), and checks its own bounding box
    before calling it done. Ask for motion in the prompt and it can add
    looping and interaction animations too. Minutes rather than seconds; see
    [Model quality](#model-quality).
  </Step>
  <Step title="Icons">
    Generated as a bitmap glyph at the size you pick, ready to assign to a
    character. See [Icons](/icons).
  </Step>
  <Step title="Sounds">
    Generated as several **takes** from one prompt; you keep the best. The
    audio is converted to the one format Minecraft loads, and what the sound
    *does* is decided by the event name you give it, not by the prompt. See
    [Sounds](/sounds).
  </Step>
</Steps>

## Reference images

Every image kind (blocks, items, models, icons) can take a **reference
image** alongside the prompt: drop a picture on the Generate form and the AI
works from it as well as your words. A model built from a reference picks up
its shape and palette, which is often the shortest route to "like this, but
Minecraft".

A reference is consumed by the run it was attached to. Iterating afterwards
works from the asset, not the old reference.

## Model quality

A model generation has a quality setting, **Low**, **Medium** or **High**,
which decides how hard the builder thinks at each step and how many build
steps it gets. **High is the default**, and it alone does a refine pass:
when it finishes early, it re-inspects its own model and spends what's left
adding the detail that sells it.

| Quality | What you get | Typical time |
| --- | --- | --- |
| Low | One pass, no second look. Cheapest and quickest | ~1–4 minutes |
| Medium | Generates, looks at the result, fixes what's wrong | ~2–7 minutes |
| High | Thinks hardest and longest, largest build budget, plus the refine pass | ~3–10 minutes |

Every generated model keeps its **Build log**: what the builder thought,
every action it took, and its summary, as an expandable card under the
Prompt card on the model's page. When a result surprises you, the log usually
says why.

<Callout type="note">
  The credit estimate you see up front is approximate. The charge settles to
  what the run actually used, and unused reservation is refunded. A model run
  is long enough that you don't have to watch it: leave the tab, and
  [notifications](/notifications) can tell you when it lands.
</Callout>

## Writing a prompt

Be specific about **material, colour and structure**. Be vague about pixels:
the model can't count them for you, and asking it to will cost you the parts
it's good at.

<CardGroup>
  <Card title="Works" icon="sparkles">
    *weathered copper roof tiles, blue-green patina, strong diagonal grain*
  </Card>
  <Card title="Works less well" icon="wrench">
    *a nice block, 4px border, dark at the bottom, make it pop*
  </Card>
</CardGroup>

Some things worth naming explicitly:

- **The material.** "Oxidised copper" gets you further than "green metal".
- **The wear.** New, weathered, cracked, mossy. This is most of what makes a
  texture look like it belongs in Minecraft.
- **The structure.** Planks, tiles, bricks, panels, woven. Give the eye a
  repeating unit.
- **What it sits next to.** "reads next to deepslate" is a real constraint and
  the model will use it.

<Callout type="tip">
  Prompt for the thing, not for the fix. If a texture is close but too busy,
  say "same block, fewer distinct colours, calmer surface" rather than trying
  to describe the finished pixels.
</Callout>

## Iterating

You can send an existing asset back for another pass with a new instruction.
For a texture, that pass sees the current pixel grid, so it edits rather than
starts over. That's usually better than re-rolling the original prompt: you
keep the palette and silhouette you already liked. For a model, **Edit with
AI** is more targeted still: the builder inspects the model's structure
first and changes only what the instruction asks, instead of regenerating
the whole thing.

<Callout type="warning">
  Iterating still costs a generation, and a texture pass can drift. If you've
  painted a texture by hand, duplicate it first: that path edits the whole
  grid, not just the part you mentioned.
</Callout>

## Knowing when to stop generating

The honest rule: once the silhouette and palette are right, switch to the
editor. Hand-fixing eight pixels takes fifteen seconds and gets you exactly
what you meant; three more prompts take two minutes and get you something
slightly different each time.
