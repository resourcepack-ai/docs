# Dialogs

A dialog is the screen a server opens on a player — added in Minecraft
**1.21.6**. It is not a container: it has no slots, and its buttons are real
buttons that run real commands.

What makes it worth drawing is that a dialog is made of **text**. Its title,
the lines in its body and every button's label are text components, and a text
component can be a font glyph. So a pack can put a whole 256×256 picture in the
body and a piece of drawn artwork in each button's face, and what comes back is
a screen that looks nothing like Minecraft with buttons that still work.

## Two styles

When you make a dialog you choose its **Style**, in both the Generate and the
Draw door:

- **UI** is a drawn menu: a 256×256 picture with our own buttons, cards and a
  panel if you want one, fitted to a single screen. Everything from
  [Drawing one](#drawing-one) to [Generating one](#generating-one) below is
  about this style.
- **Dialog** is **Minecraft's own look** — the way the big servers' store,
  checkout and guide screens look. The game's font and grey buttons laid
  straight over the blurred world, the title in the game's own header, a Close
  button in the game's own footer, and a body that **scrolls with the game's
  scrollbar** when it is taller than the screen. See
  [The Dialog style](#the-dialog-style).

The style is chosen when a dialog is made and stays with it.

<Callout type="warning" title="A dialog needs a plugin, and 1.21.6">
  The picture is in your resource pack. The dialog itself is not — it is
  datapack data, which a resource pack cannot carry. [RP
  Engine](/rp-engine) is what writes it on the server and opens it. On
  anything older than 1.21.6 the game has no dialog screen at all; a
  [GUI](/guis) is the older way to do the same job and works everywhere.
</Callout>

## Drawing one

A dialog is edited in the same editor a GUI is, with one difference: instead of
slot guides it has **button guides**, and those are the whole layout.

Each dashed box is where the game will draw one of the dialog's buttons. Paint
inside a box and that artwork becomes the button's face; leave it empty and the
button keeps vanilla's grey widget and your words. Everything outside the boxes
is the panel — the frame, the heading, whatever you want behind it.

The boxes move when the dialog does. Add a button, change one's width, switch
from two columns to three, and the guides move to where the game will put them.
So set the buttons up first and paint into them second.

To resize the dialog, click bare sheet so nothing is selected, then drag the
grips on its outline — the top edge, the top corners or the sides. The window
stays centred, so both edges move together. You can also type a size under
**Size** in the Dialog panel. Either way the background moves with it: its
frame and the strip behind the buttons keep their exact pixels while the rest
stretches, and the heading, words and pictures stay the same distance from
the edge they are nearest. Buttons follow the layout. One resize is one undo.

If a dialog made before this has background hanging below its last row of
buttons, the panel offers **Pull it back in**, which moves just that bottom
edge back inside the window.

The Text tool and free-text components offer 1×, 2×, 3× and 4× lettering.
Larger words need more room on the 256×256 sheet, so check their placement
before syncing.

Two components are made for the kind of screens big servers build:

- **Formatted text** is a page of words written like markdown: `# Heading`,
  `## Subheading`, `- bullet`, `> note`, `---` for a rule and `**word**` to
  highlight. It wraps to the box you drag, in three colours you choose (body,
  headings, and the highlights, bullets and rules). Use it for rules pages,
  getting-started guides and patch notes.
- **QR code** draws a link as a code players scan with their phone — a store
  checkout, a Discord invite, a vote page. Set the link on the right. It is drawn
  as large as its box allows in whole pixels, since a scanner cannot read
  half-pixels. On a dialog it also becomes a clickable area that opens the same
  link, for players without a phone to hand. Change the link later and the
  clickable area follows.

Button faces are held two pixels in from their boxes on every side, so the
panel's edge stays visible under the last row. The dashed guides show the full
native click areas. **Space between buttons** adds more room between the drawn
faces, in steps of two pixels, and shows how far apart they will look; it
changes the artwork inside the click areas, not where Minecraft puts its
buttons.

Buttons below the panel fill their box except for its outer pixel. That pixel
is the rim of Minecraft's own button, black normally and **white when the
pointer is over it**, so the buttons light up on hover without a shader. The
canvas shows it: hover a button there and its rim turns white. (Hovering
changes nothing else about a dialog button, not even the label's colour, so
there is no way to swap a whole second picture in on hover without a core
shader.)

Minecraft draws its own grey button first and your artwork on top, so any
transparent pixel inside a button's box shows that grey through. The canvas
shows the grey button underneath for exactly that reason — if you see grey
round a rounded corner, so will your players. With **Drawn faces** off, the
canvas shows the game's buttons with their fallback words instead.

## What a button can do

One thing each, chosen in the Dialog panel beside the canvas:

| Action | What happens |
| --- | --- |
| **Run command** | The player runs it, with their own permissions. |
| **Suggest command** | It goes into their chat box unsent. |
| **Open link** | The client asks before following it. |
| **Copy text** | Onto their clipboard. |
| **Open another dialog** | Pick one of the pack's dialogs from the list — it opens straight away. |
| **Nothing** | Which, with "After a press: Close", is what an Ok button is. |

A command runs **as the player**, so it obeys their permissions. A button that
needs more than they have wants a command the server has set up for it, not a
higher-privileged button — there is no such thing.

Minecraft reads a whole dialog at once, and one action it cannot accept stops
the entire dialog opening. So a button whose action would be refused — a link
that does not start with `http://` or `https://`, an id that is not a valid
dialog id, an empty command — is sent with no action at all (it just closes
the dialog), and the editor marks it with a warning until it is fixed.

A button that opens another dialog from the same pack carries that dialog with
it, so it opens without a server restart. "Another id…" in the same list takes
any other dialog id, which the server has to know already — one of
Minecraft's, or one from a datapack.

## Clickable areas

Buttons are not the only thing a player can click. Any part of the picture — a
reward tile, a shop card, a row in a settings list, an icon — can be a
**clickable area** with its own action and its own tooltip, and it needs no
button behind it. It is how the richest server menus are built: a week of
reward days, each one clickable, each one explaining itself on hover.

Pick the **Areas** tool (A) from the rail and drag a box over the picture. With
the box selected, the panel beside the canvas sets what a click does (the same
choices a button has) and its tooltip. Drag a box to move it, pull its grips to
resize it, and press Delete to remove it. Areas on a piece move with it when
you drag the piece or resize the dialog.

Tooltips are written as plain lines and coloured the way server menus colour
theirs:

```
Tuesday - Free

Reward
∙ 250 Coins

Click to claim!
```

The first line is the title. A line above a list of `∙` items is that list's
heading, a line starting ✔ is green, one starting ⌀ or ✘ is red, and one
starting "Click" is yellow. The panel shows a preview, and hovering an area on
the canvas shows exactly what a player will see.

<Callout title="Clickable in whole lines">
  The game finds a click by the line of text it lands on, and a dialog's lines
  are 9 pixels tall — so an area is clickable on every line its box crosses,
  across its exact width. The Areas tool shades the real clickable shape. The
  topmost line of a dialog holds the picture itself and cannot be clicked, so
  an area needs a little room above it; the dialog grows by a line if it has to.
</Callout>

One difference from a button: `$(key)` from an input is filled in for buttons
only. A click on the picture runs its command exactly as written.

## Inputs

A dialog can ask for something: a text box, a checkbox, a list to pick from or
a slider. Each has a **key**, and any button's command can write `$(key)` and
get what the player put there.

```
tp @s $(destination)
```

## Fitting on the screen

Minecraft gives a dialog the screen's height less a 38-pixel header and footer,
and anything taller **scrolls**: the buttons start below the edge of the screen
and a scrollbar appears. That depends on each player's screen and GUI scale.
On the Auto GUI scale, which most players use, a 1440p or 4K monitor is only
240 GUI pixels tall and a 1080p one 270.

The **In game** box under Size measures your dialog and says which of those
screens it fits, and the readout above the outline says the same while you
drag. Only rows with artwork on them count: transparent space above your panel
costs nothing, so a shorter window is how to make a dialog fit. When it does
not fit, **Shrink to fit every screen** finds the tallest window that fits a
240-pixel screen and resizes to it. The darkened strip under the last row of
buttons is never drawn in game.

## Layout and editing

**Buttons** go either **in the panel** or **below the panel**. In the panel
they are a grid at the bottom of your art, in as many columns as you choose —
and because Minecraft stops drawing a dialog at its last row of buttons, a
button there always sits right on the panel's bottom edge. Below the panel,
Minecraft draws one or two buttons under the dialog instead (the footer), so
your art keeps a frame and a margin all the way round; this is how most server
menus do their Close. The canvas draws footer buttons just under the window,
where they sit on a small screen — on a taller one they are further down.
Generated dialogs always put them in the panel.

Use **Add button** in the Dialog panel, then select a button to edit its face,
label, tooltip and action. Undo covers these too — adding, removing and
reordering buttons, their widths, columns and inputs — alongside everything
you paint. Layout, inputs and behaviour have separate expandable
sections. Input previews show the separate label and field for text inputs,
the checkbox and its label, and the initial selection or slider value at the
game's pixel scale. They are not painted into the exported artwork. Other
resource packs can change the native controls' appearance. Save writes artwork
and actions together. **Sync saves pending edits first** and stops if saving
fails, so the game receives the layout you are looking at.

Minecraft adds a warning button beside every dialog title. **Show warning icon**
in Behaviour and alignment is off by default. This hides its sprite in the
resource pack; the button remains clickable. Minecraft uses one sprite for the
whole pack, so the choice applies to every dialog in that pack.

After an editor update, reopening a dialog can refresh its generated button
components. Save and sync it to send the updated artwork and layout to Minecraft;
an already downloaded resource pack keeps its previous pixels and font metrics.

## Generating one

Describe the screen and the generator decides its layout, what it says, what
everything is called and how wide the window is. It builds the screen out of
rows and columns — a header, a list of categories down the left, three things
side by side — and a layout engine works out where every piece goes, so
nothing overlaps and nothing runs off the window.

Set **Layout** to choose one yourself, or leave it on **Decide for me** and the
generator picks from what the screen is for. Choosing one shows an example of
it under the picker:

- **Sidebar** — categories down the left, with the one you are in highlighted,
  and its content on the right. Stores, profiles and menus with sections come
  out this way.
- **Columns** — two to four things side by side to compare, each with an icon,
  a price or a value, a button and what it includes. Ranks, kits, crates and
  plans come out this way.
- **Tiles** — a grid of clickable tiles, each with an item icon, a word above
  and a number below, and a state you can read at a glance: claimed tiles dim
  and get a tick, locked ones darken and get a padlock, and the one you can take
  now gets a gold rim. Daily rewards, shops and perks come out this way.
- **Rows** — a list of clickable rows, each with an icon, a label and a value
  chip that is green when on and red when off. Settings, toggles and warp menus
  come out this way.
- **Guide** — a page to read, set as a Formatted text component with headings,
  bullets and highlights, with its contents down the left. Rules, guides and
  changelogs come out this way.
- **Simple** — a few words and one or two buttons, for notices and
  confirmations.

A generated dialog always has its own buttons **in the panel** — usually just a
Close, or a pair for a confirmation. Everything else you click on it is a
clickable area of the picture: category buttons, tiles, rows and anything else
that has a tooltip. Under **Extras**, **Progress bar** guarantees a bar for a
streak, tier or goal, and **QR code** puts a code of the link you type on the
screen, clickable too. The QR code is the one thing on a generated dialog that
arrives wired, because the link is yours rather than the generator's.

Every clickable area arrives with a tooltip written like a server's item lore —
the reward, the cost, the requirement and a status line. Numbers on the screen,
such as a balance or a key count, are sample values for you to change. The
window is sized to exactly what is on it and fitted to a 240-pixel screen: if a
design is too tall, the generator tightens the spacing, shrinks large icons and
drops small print before it gives up.

For the UI style, **Background** decides the look. **None** is the clean look of the big servers'
menus: no panel, the content floating over the game, and the title in the
game's own header above the dialog. **Flat** puts it on a composed panel with a
frame and a title plaque. **Drawn** does the same with a material the image
model draws, or on a Simple screen spends that one image on a picture instead.
Neither None nor Flat asks the image model for anything.

Headings, pages and QR codes arrive as editable components, and each section of
the layout as its own layer, so you can move and restyle them without painting
over anything.

<Callout title="It names the buttons; you wire them">
  Nothing invents a command. A generated dialog arrives with its buttons and
  clickable areas named and described, and their actions empty, because a
  command is a thing with consequences on your server.
</Callout>

## The Dialog style

A Dialog-style dialog looks like a screen Minecraft itself made. Nothing is
painted behind it: the words, buttons and icons sit straight on the darkened,
blurred world, in the game's own font with its shadow. The title is the one the
game draws in its header, with the game's warning button beside it, and the
button at the bottom is the game's own, in its footer. When there is more on
the screen than fits, the game scrolls it and shows its own scrollbar on the
right — so a guide can be as long as it needs to be.

It can be up to **388 pixels wide** (nearly the whole width of a small screen)
and about **1,000 pixels tall**, and it is built out of the same rows, columns
and grids as a generated UI dialog, with these pieces:

| Piece | What it is |
| --- | --- |
| **Button** | The game's grey 20-pixel button. **Selected** makes it gold, the way a store marks the category you are in; **Greyed out** is the game's disabled button; the label can have its own colour, and a sidebar's buttons can read from the left. A button colour tints the same button, bevels and all. |
| **Link** | A line of clickable words, for a guide's contents. The current page is white and underlined, and sub-pages can be indented. |
| **Text** | Words in the game's own colours. Titles are twice the size, headings bold. |
| **Chip** | A dark, see-through box for a balance, a count or a rank tag. |
| **Setting row** | A full-width button with a value on the right, green when on and red when off. |
| **Tile** | A dark card with a word, an icon and a caption, and a state: ready (gold), claimed (dimmed, ticked) or locked (padlocked). |
| **Check line** | A ✔ or a ✘ in front of a word, for what a rank includes. |
| **Label and value** | A label on the left and a value on the right, for receipts and stats. |
| **Page of text** | Markdown-lite: `# Title` twice the size, `## Heading` in bold, `### Heading` in gold, `- bullets`, `> notes`, `**words**` in gold, `---` a rule. |
| **Progress bar**, **QR code**, **Icon**, **Divider**, **Space** | As they sound. A QR code carries its own link and opens it when clicked. |

Anything with a tooltip is clickable, and so is every button, link, tile and
setting row. Tooltips are written the same way as for [clickable
areas](#clickable-areas).

### Editing one

A Dialog-style dialog opens in its own editor, because there is no picture to
paint — the screen is drawn from its layout every time. In the middle is the
game's screen at the size a real monitor gives it (426×240 is a 1440p or 4K
monitor on the Auto GUI scale, 480×270 a 1080p one), and it behaves like the
game: the mouse wheel scrolls it, hovering a clickable thing shows its tooltip,
and **Clickable areas** shades where a click will land.

Click anything in the preview, or pick it from the **Outline** on the left, and
the panel on the right edits it: its words, style, colours, icon and width, its
tooltip, and under **When clicked** what it runs — the same choices a button
has. **Add after** (or **Add inside**, on a row or column) adds a piece, and the
arrows, **Duplicate** and **Delete** rearrange them. Click the empty space around
the content, or press Escape, to get back to the dialog's own settings: its
title, its width, its footer (one button, or a yes/no pair) and how it behaves.
Click the footer button itself to set its words and what it runs. **JSON** shows
the whole layout as the tree the generator writes, if you would rather edit
that. Changes save on their own; Undo and Redo cover everything.

### Clickable in whole lines

The game finds a click by the 9-pixel line of text it lands on, so a clickable
thing is clickable on every line it covers at least half of. Two buttons
stacked with a few pixels between them split the line they share by which
covers more of it. **Clickable areas** in the editor shows the real shape.

### Generating one

Choose **Style: Dialog** in the Generate sheet. **Layout** and **Extras** work
as they do for the UI style, and the example under the picker shows each layout
in the game's look; **Size** and **Background** are not asked, because a
Dialog-style dialog is as wide as its content and has nothing behind it. It
never uses the image model. The generator writes Title Case rather than
capitals, puts a store's categories in their own colours with the current one
gold, and lets a guide's page run long, since the game will scroll it.

## Getting it onto a server

Pair the pack with a server running RP Engine and push it, the same way you
[test anything else](/testing/plugin). Then:

```
/rp dialogs                     # what the server has
/rp dialog studio:quest-board   # open one
```

The panel in the editor has the exact command for the dialog you are looking
at.

<Callout title="A pushed dialog opens straight away">
  No restart for ordinary opening. On supported Mojang-mapped servers, RP Engine
  decodes the JSON with the server's own codec and sends the dialog directly,
  including multiline text. Other servers use the inline command path, with a
  registered datapack entry as a last fallback for content that path cannot carry.
  Push the updated resource pack before opening changed artwork.

  There is one thing a restart still adds. RP Engine also writes your dialogs
  into a datapack of its own, and after the next restart each one is a real
  `namespace:id` — which is what lets you name it from your own datapack, from a
  command block, or from a `minecraft:show_dialog` click event you wrote by
  hand. That half is registry data, and registry data is read when the server
  loads its world. `/minecraft:reload` does not do it: a reload rebuilds
  recipes, advancements, loot and tags, and this registry is built with the
  world instead.
</Callout>

## If the picture sits a few pixels off

Where the game puts a dialog's body relative to its buttons is layout inside
the client, and it is not something a pack can read — so the placement here is
worked out rather than looked up, and a Minecraft release that moves a padding
moves every drawn dialog with it.

The **Nudge** fields in the Dialog panel are the fix. Type the offset, save,
look again. It is stored on that dialog, so it survives everything else you do
to it.
