# Your own server

Our test server is fine for a quick look, but eventually you want a pack on
*your* server, in *your* world, in front of the people you build with. That's
what the plugin is for: once a player has linked, studio can push a pack — or
hand them a specific model item — straight to that player in seconds, without
anyone touching `server.properties` or uploading a zip anywhere.

<Callout type="note" title="Requirements">
  A Paper or Spigot server on **1.21.4 or newer**, running **Java 21+**, and
  permission to install plugins on it.
</Callout>

## Install the plugin

<Steps>
  <Step title="Download the jar">
    ```
    https://cdn.resourcepack.ai/resourcepackai.jar
    ```
  </Step>
  <Step title="Drop it in /plugins">
    Put the jar in your server's `plugins/` folder, alongside everything else.
  </Step>
  <Step title="Restart the server">
    A `/reload` won't do it — plugin jars are only picked up on a real
    restart. Check the console for the plugin's startup line.
  </Step>
</Steps>

<Callout type="note" title="Why 1.21.4">
  Placed models use display entities and string-valued custom model data,
  which don't exist on older versions. There's no build that works on 1.8 —
  the features it exists to deliver aren't there to use.
</Callout>

## Link a player

<Steps>
  <Step title="Get a pairing code from studio">
    Open the live-test panel for the pack you want to push. It shows an
    8-digit code as a ready-to-paste command. There's no "generate" button —
    a pack gets its code the first time you look.
  </Step>
  <Step title="Run /link in game">
    ```
    /link 48213097
    ```

    Whoever runs the command claims the code, so the pairing is to that
    **player**, not to the server. Two people on the same server can be linked
    to two different packs at the same time.
  </Step>
  <Step title="Push the pack">
    Studio shows the player as connected. Push, and their client downloads and
    applies the pack without leaving the world.
  </Step>
</Steps>

<Callout type="note" title="A code belongs to a pack, not to a session">
  The code stays the same for that pack — it doesn't expire, and you can
  re-run `/link` with it after a restart. Studio only mints a replacement
  once the old pairing has been unlinked.
</Callout>

<Callout type="note" title="If a client turns the pack down">
  Studio reports a push as sent, because that's all this end can see — the
  client decides separately, and it can refuse without ever showing a prompt
  if that server entry's **Server Resource Packs** setting is "Disabled". When
  that happens the plugin walks the player through fixing it in chat, step by
  step. Nobody else on the server sees those messages.
</Callout>

## Commands and permissions

| Command | Permission | Does |
| --- | --- | --- |
| `/link <code>` | `resourcepackai.link` — everyone | Claim a pairing code |
| `/rpai status` | `resourcepackai.admin` — op | Show the connection and current pairings |
| `/rpai reconnect` | `resourcepackai.admin` — op | Force a reconnect to the sync service |

The plugin only holds a connection open while something is actually linked, so
a server with no active pairings sits idle.

<Callout type="note">
  `/link` is open to every player on purpose. A claim only ever affects the
  player who ran it — they get a pack on their own client — so there's nothing
  to gate, and restricting it makes `/link` read as "Unknown command" to
  everyone else, which looks like a broken plugin.
</Callout>

## Bedrock players

If your server runs [Geyser](https://geysermc.org/) alongside the plugin,
linked Bedrock players are handled too — they link with `/link` like anyone
else, and studio tags them as Bedrock in the panel.

The one visible difference is how a pack arrives. Bedrock clients only accept
resource packs while joining, so applying one means the player is transferred
back to the server they're already on — a few seconds of rejoin — and served
the pack on the way in. Studio tells you this before it happens, and the
pairing survives it.

Placed models are visible to Bedrock players: the pushed pack defines each
model as a native Bedrock entity, and the plugin spawns one per placement for
each Bedrock session. Animations play **client-side** from the pack's own
keyframes, which is actually smoother than the Java side's server-driven
playback.

<Callout type="note">
  New models added since a player's last pack apply ride in on the next one —
  the reconnect that installs the pack is also what teaches their client the
  new models. No server restart needed.
</Callout>

## Troubleshooting

| Symptom | Usually means |
| --- | --- |
| `/link` is an unknown command | The jar didn't load — check `plugins/` and restart properly |
| "Unknown code" | It expired or was already claimed. Generate a new one |
| Pack pushes but nothing changes | The client declined it. The plugin tells that player how to fix it in chat — it's the **Server Resource Packs** setting on the server entry |
| Works for you, not for others | Each player links separately; one `/link` doesn't cover the server |
| Linked, then went quiet | The pairing drops when the player quits. Re-link on rejoin |
