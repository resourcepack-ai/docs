# Your own server

[RP Engine](/testing/plugin) gives you [our test server](/testing/test-server) on your own
server. Not a cut-down version of it: pack pushes, placing and picking up
models, the animation engine, sound playback and custom GUI screens all work
exactly as they do on <ServerAddress />.

What you get on top is that it's *your* map, *your* builds, and whoever you
play with standing in it. Once a player has linked, the Studio pushes a pack
straight to them in seconds, without anyone touching `server.properties` or
uploading a zip anywhere.

<Callout type="note" title="A building tool, not a distribution channel">
  Linking is per player, so it's how you and the people building with you see
  a pack while it's being made. To serve a pack to every player, use
  [Distribution](/distribution), or point `server.properties` at an
  [exported](/exporting) `.zip`, which needs nothing of ours installed.
</Callout>

<Callout type="note" title="Requirements">
  A Paper, Spigot or Folia server on **1.19.4 or newer**, running **Java 17+**,
  and permission to install plugins on it.
</Callout>

## Install the plugin

<Steps>
  <Step title="Download the jar">
    ```
    https://cdn.resourcepack.ai/RPEngine.jar
    ```
  </Step>
  <Step title="Drop it in /plugins">
    Put the jar in your server's `plugins/` folder, alongside everything else.
  </Step>
  <Step title="Restart the server">
    A `/reload` won't do it: plugin jars are only picked up on a real
    restart. Check the console for RP Engine's startup banner: its
    version, its links, and what it loaded.
  </Step>
</Steps>

<Callout type="note" title="Why 1.19.4">
  Placed models are made of display entities, which 1.19.4 added. Below 1.21.4
  a few things are reduced, and the plugin says which at startup.
</Callout>

## Link a player

<Steps>
  <Step title="Get a pairing code from the Studio">
    Press **Sync** on the pack and choose **Testing on your own server
    instead?** to get an 8-digit code as a ready-to-paste command.
  </Step>
  <Step title="Run /rp sync in game">
    ```
    /rp sync 48213097
    ```

    Whoever runs the command claims the code, so the pairing is to that
    **player**, not to the server. Two people on the same server can be linked
    to two different packs at the same time.
  </Step>
  <Step title="Push the pack">
    Studio shows the player as connected. Push, and their client downloads and
    applies the pack without leaving the world.
  </Step>
</Steps>

<Callout type="note" title="A code belongs to a pack, not to a session">
  The code stays the same for that pack. It doesn't expire, and you can
  re-run `/rp sync` with it after a restart. Studio only mints a replacement
  once the old pairing has been unlinked.
</Callout>

<Callout type="note" title="If a client turns the pack down">
  Studio reports a push as sent, because that's all this end can see: the
  client decides separately, and it can refuse without ever showing a prompt
  if that server entry's **Server Resource Packs** setting is "Disabled". When
  that happens the plugin walks the player through fixing it in chat, step by
  step. Nobody else on the server sees those messages.
</Callout>

## Commands and permissions

| Command | What it does |
| --- | --- |
| `/rp sync <code>` | Pair yourself with a pack in Studio |
| `/rp sync add <player>` | Share your pushes with someone building alongside you |
| `/rp sync stop` | End your sync |

All of them need `rpengine.sync`, which defaults to operators; grant it to your
builders. The full list is on [Commands and permissions](/rp-engine/commands).

## Bedrock players

If your server runs [Geyser](https://geysermc.org/) alongside the plugin,
linked Bedrock players are handled too: they pair with `/rp sync` like anyone
else, and Studio tags them as Bedrock in the panel.

The one visible difference is how a pack arrives. Bedrock clients only accept
Resource Packs while joining, so applying one means the player is transferred
back to the server they're already on (a few seconds of rejoin) and served
the pack on the way in. Studio tells you this before it happens, and the
pairing survives it.

Placed models are visible to Bedrock players: the pushed pack defines each
model as a native Bedrock entity, and the plugin spawns one per placement for
each Bedrock session. Animations play **client-side** from the pack's own
keyframes, which is actually smoother than the Java side's server-driven
playback.

<Callout type="note">
  New models added since a player's last pack apply ride in on the next one:
  the reconnect that installs the pack is also what teaches their client the
  new models. No server restart needed.
</Callout>

## Troubleshooting

| Symptom | Usually means |
| --- | --- |
| `/rp` is an unknown command | The jar didn't load. Check `plugins/` and restart properly |
| "Unknown code" | It was mistyped or the pairing was unlinked. Get the code again from Sync |
| Pack pushes but nothing changes | The client declined it. The plugin tells that player how to fix it in chat: it's the **Server Resource Packs** setting on the server entry |
| Works for you, not for others | Each player pairs separately; one `/rp sync` doesn't cover the server. `/rp sync add <player>` shares yours |
| Linked, then went quiet | A push lasts until the player leaves. Press Sync again after they rejoin |
| "Lost the connection to that server", but the server is fine | The plugin's link to the sync service dropped. It reconnects and re-announces every pairing on its own within a few seconds, so push again |
