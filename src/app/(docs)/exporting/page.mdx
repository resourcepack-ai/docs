# Exporting

You never have to export to test a pack. Pushing to a linked player never
produces a file you have to handle, so export is for taking the pack
*elsewhere*: a launcher, a server host, a friend, a marketplace listing.

## What you can export

The Export dialog splits these two ways, because only half of them are
resource packs.

**Default Pack** — a pack you install or serve yourself, no plugins involved:

| Export | File | When you'd pick it |
| --- | --- | --- |
| **Java pack** | `.zip` | The ordinary Resource Pack. Goes in `resourcepacks`, or to a server host |
| **Bedrock pack** | `.mcpack` | Everything with a Bedrock equivalent, converted. Double-click to install. See [On Bedrock](#on-bedrock) |

**Plugin Support** — not resource packs. On a server running one of these, the
plugin builds the pack, and what you're downloading is the content it builds
from:

| Export | File | When you'd pick it |
| --- | --- | --- |
| **Model Engine** | `.zip` | `.bbmodel` blueprints for a server running [Model Engine](https://git.mythiccraft.io/mythiccraft/model-engine-4) |
| **ItemsAdder** | `.zip` | A `contents` folder for a server already running [ItemsAdder](https://wiki.itemsadder.com/) |
| **Nexo** | `.zip` | Items, furniture, custom blocks and glyphs for a server already running [Nexo](https://docs.nexomc.com/). See [below](#nexo-and-oraxen) |
| **Oraxen** | `.zip` | Items, furniture, custom blocks and glyphs for a server already running [Oraxen](https://docs.oraxen.com/). See [below](#nexo-and-oraxen) |
| **CraftEngine** | `.zip` | Items, furniture, real custom blocks, images and chat emoji for a server already running [CraftEngine](https://modrinth.com/plugin/craftengine). See [below](#craftengine) |

All seven are built on demand from what's currently in the editor. There's no
build step to remember and nothing to re-upload between edits.

<Callout type="warning" title="Animations don't survive a Java export">
  In the Java `.zip`, animations and bones are stored as extra fields on the
  model JSON. Vanilla ignores fields it doesn't recognise, so the pack is
  perfectly valid and the model just sits there, static; playback needs our
  plugin. The Bedrock `.mcpack` is the opposite, since Bedrock has native
  keyframe animation and they convert into the real thing. See
  [Animations](/animations).
</Callout>

## On Bedrock

Bedrock is a different game with a different pack format, so the `.mcpack` is
a conversion rather than a copy. What converts:

| Asset | On Bedrock |
| --- | --- |
| Models | A Bedrock entity with your geometry, animations as native keyframes |
| Block and item reskins | Under Bedrock's own texture names |
| Custom items | Their sprite, or the model's icon, as the item's icon |
| Sounds | With your event names, so custom sounds play |
| Armour | The same sheets, under Bedrock's armour names |
| 3D armour | Each piece drawn on the body, when worn on a server running RP Engine |
| Icons | Drawn into Bedrock's glyph sheets |
| Pack icon | Yes |

Models and 3D armour are defined in the `.mcpack` but need something to put
them in the world: on a server, that is [RP Engine](/rp-engine/bedrock) with
Geyser. A `.mcpack` installed on its own shows the reskins, sounds, armour and
icons, and no models.

What doesn't convert, because Bedrock has no way to draw it: GUI screens, the
HUD, shaders, dialogs, emotes, vehicles, models placed as blocks, per-face block
splits and item variants. Each asset's own page says more under
**On Bedrock**.

## ItemsAdder

If your server already runs ItemsAdder, it builds and serves the resource pack
itself — so what you want from us is the *content*, not a second pack. This
export is your whole pack as ready-made ItemsAdder content, with the config
files written for you.

```
contents/<your-pack>/
  configs/items.yml            models, 2D items and custom blocks
  configs/font_images.yml      icons
  resourcepack/assets/
    <your-pack>/               your items' models, textures, icons and sounds
    minecraft/                 the vanilla files your pack replaces
```

Everything goes wherever ItemsAdder expects that kind of thing:

| In your pack | Becomes |
| --- | --- |
| 3D model | an item with a custom model |
| Custom block | an ItemsAdder block (`REAL_NOTE`) that drops itself when mined |
| Vehicle | furniture you can sit in, with a hitbox measured from the model |
| 2D custom item | an item — ItemsAdder builds the model from the sprite |
| Icon / glyph | a `font_image` — ItemsAdder gives it a new character |
| Block or item reskin | a vanilla file replacement |
| GUI screen that replaces a vanilla file | a vanilla file replacement |
| GUI overlay | a `font_image` plus the title string that positions it |
| Sound | a sound in your pack's namespace, and a replaced vanilla sound stays replaced |

The zip already contains `contents/`, so merge it into `plugins/ItemsAdder/`
— dropping it *inside* the existing `contents/` gives you
`contents/contents/` and ItemsAdder finds nothing. Then on the server:

```
/iazip                                  rebuilds the pack (this reloads too)
/iaget <namespace>:<item>               gives you one
/iagive <player> <namespace>:<item>     gives somebody else one
```

The namespace and item ids are in `configs/items.yml` — `info.namespace`,
and each key under `items:`. Both are lowercased with non-letters turned into
underscores, so a model called "Floating Sword" in a pack called "My Pack"
becomes `/iaget my_pack:floating_sword`.

<Callout title="Why this doesn't collide with your existing content">
  A resource pack overrides per *file*, not per entry — so a normal pack
  dropped onto an ItemsAdder server replaces its `paper.json`, its blockstates
  and its font, taking every ItemsAdder item and emoji with them. This export
  writes none of those. It sets no `CustomModelData` either; ItemsAdder assigns
  them, so nothing here can land on a value you're already using.
</Callout>

**Custom blocks are real ItemsAdder blocks.** A model you gave a full block
carrier is placed as a note block, the same carrier it uses in the Java pack,
except ItemsAdder picks the note-block state and writes the blockstate itself.
It has a hardness of 2, a little softer than stone, sounds like stone and
drops itself; change any of that under `behaviours: block:` in `items.yml`. A
directional block turns to face whoever placed it, like a furnace. As with
every note-block block, it is a solid cube with no see-through pixels.

**Vehicles are furniture you can sit in, not drive.** ItemsAdder has no way to
drive one of our models, so a vehicle places like a chair: right-click the
ground with it, then right-click it to get in. ItemsAdder furniture has one
seat, over the middle, so the rider sits at the height of the driver's seat
and any other seats are left out; the `README.txt` says which. To drive it,
use [RP Engine](/rp-engine).

Items ride on `PAPER` because it has no vanilla behaviour to inherit. Change
`material` per item in `items.yml` if you'd rather one behaved like the item
it looks like. Models that use a *vanilla* texture keep pointing at
`minecraft:` on purpose — that texture is already in every client, so it isn't
copied.

**Icons get a new character, chosen by ItemsAdder** — not the one shown here.
Both it and we assign characters from Unicode's private-use range, and both
start at the same place, so keeping ours would land on top of an emoji you
already have and you'd see that instead. Reference the icons by their
ItemsAdder placeholder.

**Sounds play under your pack's namespace**, the way ItemsAdder's own packs
keep theirs: a sound you named `custom.laser` is `my_pack:custom.laser` on an
ItemsAdder server, ready for any ItemsAdder sound setting or
`/iaplaysound my_pack:custom.laser <player>`. A sound that replaces a vanilla
one, like `entity.creeper.primed`, also keeps its vanilla name so the game
plays it instead of its own. That goes in `resourcepack/assets/minecraft/sounds.json`,
which ItemsAdder merges with its own `sounds.json` rather than letting one
replace the other. It has done that since December 2023; on an older
ItemsAdder, delete that file or the custom block sounds go quiet. The
`README.txt` lists every sound under the name it plays as.

**The vanilla replacements apply to everyone.** Reskinned blocks, item sprites
and GUI screens change how the game looks for every player on the server, which
is a different decision from adding an item. They're all under
`resourcepack/assets/minecraft/`; delete any you don't want and run `/iazip`
again.

**Both kinds of GUI come through, differently.** A screen that *replaces* a
vanilla file — the player's inventory, the Escape menu, the HUD — needs nothing:
open the screen and it's there.

A screen drawn *over* a plugin-opened menu is positioned by negative space in
front of the image. ItemsAdder spells that `:offset_N:`, so the export writes
each overlay as a `font_image` and puts its ready-made title string in the
`README.txt`:

```
:offset_-176::gui_bank_vault:
```

Give that to whatever opens the menu — ChestCommands, DeluxeMenus, your own
plugin, or our `/gui`. The offset is measured from the sheet's own pixels, so
re-export after editing a GUI rather than reusing an old title.

Animated models come through as static: ItemsAdder doesn't play keyframes.
The export lists which ones in its `README.txt` so nothing goes missing
quietly. Models that hadn't finished generating are left out and listed the
same way — export again once they're done.

## Model Engine

Model Engine rigs animated models onto entities — hitboxes, mounts, mob
behaviour — which is a great deal more than our own plugin's playback does.
This export gives it your models as Blockbench blueprints.

```
blueprints/
  your_model.bbmodel
  another_model.bbmodel
README.txt
```

One blueprint per model — the per-part sub-models our own animation playback
uses are internal and aren't exported.

Copy the `.bbmodel` files into `plugins/ModelEngine/blueprints/`, then:

```
/meg reload                    loads them; it reports how many it found
/meg summon <model>            summons one to look at
```

<Callout type="note" title="Check the subcommand against your version">
  Model Engine's command names have moved between releases — `/meg spawn` does
  not exist on R4. Run `/meg` on its own for the list your server actually has.
</Callout>

<Callout type="warning" title="Model Engine's textures need serving, and it won't do it for you">
  `/meg reload` writes a resource pack to `plugins/ModelEngine/resource pack/`
  and stops there. A player who isn't wearing that pack watches the rig spawn,
  move and animate as a black-and-magenta checkerboard — which is this step
  missing, not a broken blueprint.
</Callout>

If ItemsAdder runs on the same server, it owns the resource pack, so tell it to
fold Model Engine's in. In ItemsAdder's `config.yml`:

```yaml
merge_other_plugins_resourcepacks_folders:
  - "ModelEngine/resource pack"
```

Then `/meg reload`, `/iazip`, and rejoin. Without ItemsAdder, merge that folder
into whatever pack your server already sends. A pack pushed from here is not
that pack and can't be — Model Engine only generates those textures once it has
loaded the blueprints.

**Models only.** Model Engine has nothing to do with block textures, item
sprites, GUI screens or icons — those belong in the Java zip or the ItemsAdder
export. Textures are *embedded* in each blueprint rather than shipped beside
it, because Model Engine builds its own resource pack from the blueprints it
loads, so an image outside the file is one it never sees.

<Callout title="These are ordinary Blockbench projects">
  If a rig looks wrong in game, open the `.bbmodel` in Blockbench. What you see
  there is what Model Engine will render, which makes it the fastest way to tell
  a conversion problem from a Model Engine configuration problem.
</Callout>

Two limits worth knowing before you build on it:

**Bones are flat.** Our bones don't nest, so no blueprint has a bone inside a
bone. Rigs animate correctly but can't do arm-inside-shoulder chains until the
editor's model format gains nesting. A model you never grouped still works —
everything goes into one `root` bone, since Model Engine needs at least one.

**A `hitbox` bone is written, sized to the model's own bounds.** Model Engine
warns `Missing hitbox` without one and its hitbox renderer needs it. Redraw the
cube in Blockbench if you want a different collision box. **`mount` and `p_*`
seat bones are not written** — those are decisions about how an entity is
ridden, which geometry can't imply.

**Vanilla textures are embedded for you.** Model Engine's pack contains only
what the blueprints carried, so a model referencing `minecraft:block/stone`
would otherwise have nothing to render — those images are fetched and packed
into the `.bbmodel` alongside your own. If a texture genuinely can't be found,
the face is left out of the blueprint rather than written untextured, because
an untextured face stops its whole bone from rendering. The `README.txt` names
any model that happened to.

### Animations don't play on their own

Model Engine won't start an animation just because the blueprint has one, and
**it has no command to play one either** — `/meg` is `reload`, `summon`,
`disguise`, `undisguise`, `trait` and `debug`, and that's the whole list. A
summoned model standing still is correct behaviour, not a broken export.

What it *does* do is auto-play a handful of names as entity states. Its
[wiki](https://github.com/Ticxo/Model-Engine-Wiki/wiki/Everything-about-animating)
lists `idle`, `walk`, `jump`, `death` and `spawn`.

<Callout type="tip" title="The quickest way to see a loop in game: call it idle">
  Name the animation **Idle** in Animate mode and Model Engine plays it on any
  summoned model with nothing else installed. Names are snake_cased on export,
  so "Idle" becomes `idle` — but "Idle Wave" becomes `idle_wave`, which is not
  a state name and won't auto-play.
</Callout>

Any other name needs something to drive it: MythicMobs mechanics, Model Engine's
API, or a separate command plugin such as
[MEGAnim](https://hangar.papermc.io/Nogard/MEGAnim) — which is not part of
Model Engine and has to be installed first.

**The triggers you picked in Animate mode don't come across.** On loop, on right
click, on range are our plugin's concept and mean nothing to Model Engine. The
`README.txt` lists each model's animation names as exported, which is what
MythicMobs wants typed.

## Nexo and Oraxen

Nexo and Oraxen build and serve the resource pack themselves, the same as
ItemsAdder, so these two exports are your pack as ready-made content for them:
item and glyph YAML written for you, plus a pack folder the plugin merges into
its own. They are one section here because they are one export with two
spellings.

```
Nexo/                                      Oraxen/
  items/<your-pack>/items.yml                items/<your-pack>/items.yml
  glyphs/<your-pack>/glyphs.yml              glyphs/<your-pack>/glyphs.yml
  pack/external_packs/<your-pack>/           pack/uploads/<your-pack>/
datapacks/<your-pack>_dialogs/             datapacks/<your-pack>_dialogs/
```

The zip already contains the plugin's folder, so unzip it straight into
`plugins/`. Then on the server:

```
/nexo reload all                    /oraxen reload all
/nexo give <player> <item>          /oraxen give <player> <item>
```

The item ids are the keys in `items.yml`, and the `README.txt` lists every one,
along with everything else the export contains.

| In your pack | Becomes |
| --- | --- |
| 3D model | furniture: hold it, or right-click a block to place it, with a hitbox measured from the model |
| Vehicle | furniture with the vehicle's seats, so players can sit in it |
| Custom block | the plugin's own custom block (a note block), mined and dropped like theirs |
| 2D custom item, 3D item | an item, keeping its name and the vanilla item a variant is built on |
| Vanilla item in 3D | the vanilla item itself, reskinned |
| Icon | a glyph: `<glyph:<pack>_<icon>>` in the plugin's text, `:icon:` in chat |
| GUI overlay | a glyph plus the title string that positions it |
| Pause-menu buttons | the redrawn buttons, as in the Java pack |
| Sounds | merged into the pack's sounds under the event names you gave them |
| Block, item, armour or GUI reskin | a vanilla file replacement |
| Dialog | a datapack folder |

<Callout title="Why this doesn't collide with your existing content">
  Both plugins merge fonts, `sounds.json` and language files instead of
  replacing them, so what this export adds sits beside what the server already
  has. The files they *do* own outright, the item wiring and the note-block
  states, are left to them: the export sets no `CustomModelData` and picks no
  block state, and the plugin writes the numbers it chose back into
  `items.yml`.
</Callout>

**Icons keep their character.** Unlike ItemsAdder, which starts in the same
place we do, Nexo and Oraxen hand out characters from U+A410 upward, so ours
can stay put. That matters because the pause-menu text and the GUI titles
already use those characters; `glyphs.yml` pins each one with `char:`.

**GUI overlays come with a title string.** The plugin draws a GUI as a glyph in
an inventory title, so the `README.txt` gives each one in the plugin's tags:

```
<shift:-48><glyph:my_pack_gui_shop>
```

Give that to whatever opens the menu: DeluxeMenus, ChestCommands, your own
plugin. As with ItemsAdder, re-export after editing a GUI rather than reusing
an old title.

**Dialogs travel as a datapack**, because neither plugin installs vanilla
dialogs. Move `datapacks/<your-pack>_dialogs/` into your world's `datapacks/`
folder, restart, and open one with `/dialog show <player> studio:<id>`. That
needs Minecraft 1.21.6 or newer.

**Oraxen gets its current spelling.** Its sections are lowercase now
(`pack:`, `mechanics:`), and it rewrites a file that uses the old capitalised
form, so the Oraxen export writes the new one. Nexo keeps `Pack:` and
`Mechanics:`, which is still what it reads.

**The vanilla replacements apply to everyone.** Reskinned blocks, items and GUI
screens are under the pack folder's `assets/minecraft/`; delete any you don't
want and reload.

Some things are drawn by [RP Engine](/rp-engine) while the game runs, and no
plugin config can express them. The `README.txt` names each one your pack has:

- **Shader objects**: RP Engine sends the text they draw on.
- **3D armour**: RP Engine poses the pieces on the wearer.
- **Animation**: models place as still furniture.
- **Driving**: vehicles place as furniture you can sit in, not drive.
- **Dialog switches and sliders bound to player settings**: they open, but
  remembering a choice needs RP Engine.

Models that hadn't finished generating are left out and listed the same way.

## CraftEngine

CraftEngine builds and serves the resource pack itself too, from one folder per
pack. This export is that folder, with the YAML written for you.

```
CraftEngine/resources/<your-pack>/
  pack.yml
  configuration/items.yml          items, furniture and blocks
  configuration/images.yml         icons, GUI overlays and chat emoji
  configuration/categories.yml     a category in the item browser
  resourcepack/                    your models, textures, sounds and replacements
datapacks/<your-pack>_dialogs/
```

<Callout type="warning" title="Run CraftEngine once before you unzip">
  CraftEngine only installs its own packs into an empty `resources/` folder,
  and custom blocks need one of them. Unzip this into a server that has
  already started with CraftEngine, not into a fresh one.
</Callout>

Unzip it straight into `plugins/`, then on the server:

```
/ce reload all                       rebuilds and resends the pack
/ce item get <your-pack>:<item>      gives you one
/ce                                  the item browser, with your pack as a category
```

The ids are the keys in `items.yml`, and the `README.txt` lists every one.

| In your pack | Becomes |
| --- | --- |
| 3D model | furniture: right-click a block to place it, sneak-click with an empty hand to turn it, with a hitbox measured from the model |
| Vehicle | furniture with the vehicle's seats, so players can sit in it |
| Custom block | a real CraftEngine block, with its own hardness, sounds and drop |
| 2D custom item, 3D item | an item, keeping its name and the vanilla item a variant is built on |
| Vanilla item in 3D | the vanilla item itself, reskinned |
| Icon | an image, `<image:<pack>:<icon>>` in CraftEngine's text, and an emoji typed as `:icon:` in chat, books, signs and anvils |
| GUI overlay | an image plus the title string that positions it |
| Pause-menu buttons | the redrawn buttons, as in the Java pack |
| Sounds | merged into the pack's sounds under the event names you gave them |
| Block, item, armour or GUI reskin | a vanilla file replacement |
| Dialog | a datapack folder |

**Custom blocks are real blocks.** CraftEngine draws one with a vanilla block
state it sets aside (`auto_state: solid`) while the server knows it as your
block, so it keeps its own hardness and drops itself when mined. Nothing here
picks the state; CraftEngine does.

**Icons keep their character, and so does everything else.** CraftEngine hands
out characters from U+E000, the same place we start, so `images.yml` pins each
icon with `char:`. A pinned character always wins, and CraftEngine moves its
own emoji out of the way. The characters your pack uses for spacing and dialog
art are not images, so CraftEngine cannot see them; `images.yml` holds them
with one invisible image, `<your-pack>:reserved`. Leave it in, or another
pack's emoji can land on one of those characters and draw as a gap.

**GUI overlays come with a title string**, in CraftEngine's tags:

```
<shift:-48><image:my_pack:gui_shop>
```

**Dialogs travel as a datapack**, as for Nexo and Oraxen: move
`datapacks/<your-pack>_dialogs/` into your world's `datapacks/` folder and
restart.

Nothing in the export uses CraftEngine's bundled templates, so it still loads
if you have removed `default_templates`. The same things RP Engine draws are
left out as for [Nexo and Oraxen](#nexo-and-oraxen), and the `README.txt`
names each one.

## Installing it

The Java `.zip` goes in your `resourcepacks` folder:

```bash
# Windows
%APPDATA%\.minecraft\resourcepacks

# macOS
~/Library/Application Support/minecraft/resourcepacks

# Linux
~/.minecraft/resourcepacks
```

A server serves it the ordinary way, from `server.properties`, and that needs
nothing of ours installed. A Bukkit, Spigot or Paper plugin can do the same
through the resource pack API, if you'd rather send it per player or swap it
at runtime. The `.mcpack` installs itself when opened.

There's no runtime dependency on us in any exported file. It keeps working if
you never open the Studio again, animated models excepted.
