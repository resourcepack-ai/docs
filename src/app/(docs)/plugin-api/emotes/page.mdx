# Emotes from code

An emote animates the **player** rather than a placed model. Their body is
replaced with a rig wearing their own skin, they're made invisible for the
duration, and they're put back exactly where they were afterwards.

Some emotes are **worn** instead — see [Stances](#stances) and [Movement
groups](#movement-groups). Those don't end when the player moves; that's the
whole point of them.

Everything here needs `rpai` — see [Plugin API](/plugin-api) for how to get it.

## Play one

<CodeTabs labels={["Java", "Kotlin"]}>
```java
EmoteResult result = rpai.emotes().play(player, "Bow");

if (!result.started()) {
    player.sendMessage("Can't do that right now.");
}
```
```kotlin
val result = rpai.emotes().play(player, "Bow")

if (!result.started()) {
    player.sendMessage("Can't do that right now.")
}
```
</CodeTabs>

That's the whole happy path. The interesting part is the result.

## Saying why it didn't work

An emote can be refused for about thirty different reasons, and they don't
have the same fix — "you're not on the ground" and "this pack was synced
without your skin" send a player to completely different places. So the API hands back a
**reason**, not a sentence, and you write the words:

<CodeTabs labels={["Java", "Kotlin"]}>
```java
EmoteResult result = rpai.emotes().play(player, "Bow");
if (result.started()) return;

player.sendMessage(switch (result.reason()) {
    case NOT_ON_GROUND   -> "You need to be standing on solid ground.";
    case ALREADY_EMOTING -> "You're already doing one.";
    case UNKNOWN_EMOTE   -> "No emote called " + result.subject()
                              + ". Try: " + String.join(", ", result.options());
    case CAST_NOT_ONLINE -> result.subject() + " isn't online.";
    default              -> "Can't do that right now.";
});
```
```kotlin
val result = rpai.emotes().play(player, "Bow")
if (result.started()) return

player.sendMessage(when (result.reason()) {
    Reason.NOT_ON_GROUND   -> "You need to be standing on solid ground."
    Reason.ALREADY_EMOTING -> "You're already doing one."
    Reason.UNKNOWN_EMOTE   -> "No emote called ${result.subject()}" +
                                ". Try: " + result.options().joinToString(", ")
    Reason.CAST_NOT_ONLINE -> "${result.subject()} isn't online."
    else                   -> "Can't do that right now."
})
```
</CodeTabs>

<Callout type="tip" title="Always have a default branch">
  The reason list only ever grows, so always have an `else` / `default`
  branch. A Kotlin `when` used as an expression needs one anyway; a Java
  `switch` will happily compile without one and then say nothing at all the
  first time we add a reason.
</Callout>

The extras on a result are worth knowing:

| Call | What it carries |
| --- | --- |
| `started()` | Whether it's playing |
| `reason()` | Why, typed. `STARTED` when it worked |
| `subject()` | Who or what the reason is about — a player's name, or the words that named no emote |
| `options()` | What *would* have worked: the emote names that exist, or the cast slots to fill |
| `borrowedSkin()` | It's playing, but wearing the pack's fallback skin rather than theirs |

`borrowedSkin()` is worth surfacing once rather than refusing over. They're
emoting — just not as themselves, because they weren't in the party when the
pack was pushed. The fix is a re-sync they can choose to do later.

## Check before you offer

<CodeTabs labels={["Java", "Kotlin"]}>
```java
if (!rpai.emotes().canPerform(player)) {
    // No rig baked for them in the pack they're wearing.
    // They joined after the last Sync — nothing they did wrong.
}
```
```kotlin
if (!rpai.emotes().canPerform(player)) {
    // No rig baked for them in the pack they're wearing.
    // They joined after the last Sync — nothing they did wrong.
}
```
</CodeTabs>

<Callout type="warning" title="Why an emote needs the player to be in the pack">
  An emote renders somebody's **skin**, and a resource pack can't reach a live
  one. So a pushed pack carries a baked copy of each recipient's skin, and a
  player who wasn't in the party at push time has no rig to wear. That's the
  one thing about emotes that surprises everybody, and `canPerform` is how you
  find out before you build them a menu they can't use.
</Callout>

## Stances

A **stance** is an emote a player puts on and keeps on. They stay in whatever
game mode they were already in and carry on playing — walking, jumping,
fighting — with the rig carried along on top of them, and the animation runs
only while they're in one of the movement states the pack author picked.

Ask `EmoteInfo` which kind you're holding:

<CodeTabs labels={["Java", "Kotlin"]}>
```java
Optional<EmoteInfo> info = rpai.emotes().info("Swagger");

info.ifPresent(emote -> {
    if (emote.isWorn()) {
        // emote.triggers() is [WALK, SPRINT] — when it animates
        rpai.emotes().play(player, "Swagger");
        player.sendMessage("/emote stop to take it off.");
    }
});
```
```kotlin
val emote = rpai.emotes().info("Swagger").orElse(null)

if (emote != null && emote.isWorn()) {
    // emote.triggers() is [WALK, SPRINT] — when it animates
    rpai.emotes().play(player, "Swagger")
    player.sendMessage("/emote stop to take it off.")
}
```
</CodeTabs>

`play` is the same call either way. What changes is what happens next:

| | An emote | A stance |
|---|---|---|
| Ends when they move | Yes | No |
| Ends when they're hit | Yes | No |
| Ends when they die | Yes | Yes |
| Game mode | Untouched | Untouched |
| Position afterwards | Put back where they started | Left where they walked to |
| Can have a cast | Yes | No |

There are six states — `IDLE`, `WALK`, `SPRINT`, `SNEAK_IDLE`, `SNEAK_MOVE`
and `JUMP` — and **exactly one holds at a time**: being off the ground wins
over everything, then crouching over sprinting and sprinting over walking, so a
crouch-walk is `SNEAK_MOVE` and never also `WALK`. While the player is in a
state the stance doesn't list, the rig rests on the animation's first frame.

`JUMP` is opt-in in a way the first four aren't. A stance that doesn't list it
treats the air as whatever the body is otherwise doing, which is what stances
did before the state existed — one authored for standing still should keep
playing while its wearer falls down a shaft, not freeze in mid-air. List it and
the air becomes a state of its own.

`SNEAK` is a seventh constant that nothing ever resolves to. Crouching used to
be one state covering both standing still and crouch-walking; the two are
separate now, and the old name is kept as an umbrella a resolved state falls
back to. So a pack built before the split goes on wearing its one crouch emote
in both, and a stance or a group that lists `SNEAK_IDLE` or `SNEAK_MOVE` means
that one exactly.

<Callout type="warning" title="A stance is not a hiding place, and doesn't need to be treated as one">
  It doesn't end on damage, which sounds like an invisibility exploit and
  isn't: the rig stands exactly where the body stands and follows it
  everywhere, so a player wearing one is as visible as a player who isn't. If
  your server still wants a rule about it — no stances in an arena, none
  during a duel — cancel `EmoteStartEvent` on your own terms, the same place
  every other gameplay rule about emotes belongs.
</Callout>

## Movement groups

A **group** is a set of emotes worn as one thing: one per movement state,
swapped as the player moves. It's what a stance can't be on its own — a rig has
one clock, so a walk cycle, a run and a crouch are three stances a player can
only wear one of at a time, and a group is the character those three add up to.

A state the group leaves alone shows the player's **own** animation: the rig is
put away and vanilla animates them until they're back in a state the group
covers. That's how a pack keeps custom walking and running while leaving
jumping exactly as it was.

Playing one is the same call as playing an emote — it's reached by name through
`play`, `perform` and `ids()`, and a name is never both:

<CodeTabs labels={["Java", "Kotlin"]}>
```java
Optional<EmoteInfo> info = rpai.emotes().info("Heavy armour");

info.ifPresent(set -> {
    if (set.isGroup()) {
        // set.triggers() is [WALK, SPRINT] — the states it wears something in.
        // The rest are the player's own animation.
        rpai.emotes().play(player, "Heavy armour");
        player.sendMessage("/emote stop to take it off.");
    }
});
```
```kotlin
val set = rpai.emotes().info("Heavy armour").orElse(null)

if (set != null && set.isGroup()) {
    // set.triggers() is [WALK, SPRINT] — the states it wears something in.
    // The rest are the player's own animation.
    rpai.emotes().play(player, "Heavy armour")
    player.sendMessage("/emote stop to take it off.")
}
```
</CodeTabs>

A group behaves as a stance in every way the table above describes, and
`isWorn()` is true for one. Two things differ, and both follow from it having
no keyframes of its own: `length()` is `0`, because each member has its own
length and which one is running depends on what the wearer is doing; and its
members are ordinary emotes that stay playable by name, editable, and usable by
a second group.

<Callout type="note" title="Nothing here is a new call">
  If your plugin already plays emotes by name, it already plays groups. Ask
  `isGroup()` only where the difference shows — a menu printing a duration, or
  anything reasoning about the animation behind a name.
</Callout>

## Duets and casts

Some emotes are authored for more than one person — a handshake, a high five.
They can't be played alone, and the cast has to be exactly the size the emote
expects. A cast emote is never a stance and is never a group's member: a
performer is placed relative to a lead who's standing still, and both of those
walk off.

<CodeTabs labels={["Java", "Kotlin"]}>
```java
Optional<EmoteInfo> info = rpai.emotes().info("Handshake");

info.ifPresent(emote -> {
    if (emote.needsCast()) {
        // emote.castSlots() is ["partner"] — labels for a prompt, not names
        rpai.emotes().play(player, "Handshake", List.of(partner));
    }
});
```
```kotlin
val emote = rpai.emotes().info("Handshake").orElse(null)

if (emote != null && emote.needsCast()) {
    // emote.castSlots() is ["partner"] — labels for a prompt, not names
    rpai.emotes().play(player, "Handshake", listOf(partner))
}
```
</CodeTabs>

The people you name are teleported into place, turned to face where the emote
puts them, and put back afterwards. Nothing is spawned and nobody is moved
until every participant and every destination has been checked — so a cast
with one person missing costs nothing rather than half-starting.

**An emote ends for everybody or for nobody.** Anyone moving, quitting or
being hit ends it for the whole group, because half a handshake is one person
shaking air.

## Building your own /emote command

Emote names are free text with spaces in them, so `"Slow clap Steve"` is
either one emote or an emote and a player, and there's no separator to tell
them apart. `perform` resolves that for you — longest leading run of words
that names an emote wins:

<CodeTabs labels={["Java", "Kotlin"]}>
```java
@Override
public boolean onCommand(CommandSender sender, Command cmd, String label, String[] args) {
    if (!(sender instanceof Player player)) return true;

    EmoteResult result = rpai.emotes().perform(player, Arrays.asList(args));
    player.sendMessage(describe(result));    // your switch from above
    return true;
}

@Override
public List<String> onTabComplete(CommandSender sender, Command cmd, String label, String[] args) {
    List<String> options = new ArrayList<>(rpai.emotes().ids());
    options.addAll(rpai.emotes().castCandidates(sender, args));
    return options;
}
```
```kotlin
override fun onCommand(sender: CommandSender, cmd: Command, label: String, args: Array<String>): Boolean {
    val player = sender as? Player ?: return true

    val result = rpai.emotes().perform(player, args.toList())
    player.sendMessage(describe(result))     // your when from above
    return true
}

override fun onTabComplete(sender: CommandSender, cmd: Command, label: String, args: Array<String>): List<String> =
    rpai.emotes().ids() + rpai.emotes().castCandidates(sender, args)
```
</CodeTabs>

`castCandidates` is empty unless the words so far name an emote that takes a
cast and there are slots left — so completing a solo emote offers nobody, and
a duet stops offering once its partner is typed.

## Stopping one

<CodeTabs labels={["Java", "Kotlin"]}>

rpai.emotes().stop(player);              // false if they weren't emoting
rpai.emotes().isEmoting(player.getUniqueId());
```

```
</CodeTabs>

## Refusing an emote on your own terms

The library refuses an emote in the air and in spectator, because those break
the emote itself. It has no opinion about arenas, minigames, regions, combat or
whose turn it is — those are yours, and
[`EmoteStartEvent`](/plugin-api/events) is where you say so.

It used to refuse one in combat too. That's gone: being hit still **ends** an
emote that is running, but whether a fight should stop somebody starting one is
a gameplay rule, and this library doesn't get to guess the rules of a server it
doesn't own. Cancel `EmoteStartEvent` on your own combat timer to bring it
back.

<CodeTabs labels={["Java", "Kotlin"]}>
```java
@EventHandler
public void onEmote(EmoteStartEvent event) {
    if (inMatch(event.getLead())) {
        event.setCancelled(true);
        event.getLead().sendMessage("Not during a match.");
    }
}
```
```kotlin
@EventHandler
fun onEmote(event: EmoteStartEvent) {
    if (inMatch(event.lead)) {
        event.isCancelled = true
        event.lead.sendMessage("Not during a match.")
    }
}
```
</CodeTabs>

Cancelling reaches the caller as `Reason.CANCELLED` with nothing attached —
the reason belongs to whoever cancelled, so say it yourself as above.
